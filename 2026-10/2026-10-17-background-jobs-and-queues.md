# 백그라운드 작업과 작업 큐: 요청을 빠르고 안전하게 끝내는 법

사용자가 버튼을 눌렀을 때 서버는 가능한 한 빨리 의미 있는 결과를 돌려줘야 합니다. 하지만 실제 서비스에는 오래 걸리거나 실패 가능성이 높은 작업이 많습니다. 이메일 발송, 이미지 처리, 알림 전송, 대량 데이터 집계, 외부 API 호출, 검색 인덱스 갱신이 대표적입니다.

이런 일을 사용자 요청 안에서 모두 처리하면 응답이 느려지고, 외부 서비스 하나가 지연될 때 전체 기능이 실패할 수 있습니다. 그렇다고 무조건 비동기로 넘기면 작업 유실·중복 실행·상태 불일치가 생길 수 있습니다. 작업 큐는 이 균형을 다루기 위한 도구입니다.

## 1. 동기 작업과 비동기 작업을 구분한다

동기 작업은 요청이 성공하기 전에 반드시 끝나야 하는 일입니다. 예를 들어 주문 생성에서 결제 승인 결과, 재고 차감 결과, 권한 변경 결과는 사용자가 즉시 알아야 할 수 있습니다.

비동기 작업은 요청이 성공한 뒤 처리해도 되는 일입니다.

- 환영 이메일 발송
- 푸시 알림 전송
- 업로드 이미지 썸네일 생성
- 검색 인덱스 갱신
- 통계 집계
- 감사 로그 외부 전송
- 대량 내보내기 파일 생성

핵심 질문은 “이 작업이 끝나지 않으면 사용자 요청을 성공이라고 말할 수 없는가?”입니다. 답이 아니오라면 비동기 처리를 검토할 수 있습니다.

예를 들어 회원 가입 요청에서는 계정 생성과 필수 권한 설정은 동기적으로 끝내야 할 수 있습니다. 반면 환영 메일 발송은 큐에 등록하고 나중에 처리해도 됩니다. 사용자는 가입 완료를 빠르게 확인하고, 메일 서비스가 잠시 실패해도 가입 자체가 실패하지 않습니다.

## 2. 작업 큐는 요청과 처리자를 분리한다

작업 큐의 기본 구조는 단순합니다.

```text
API 요청
  → 작업 메시지 생성
  → 큐에 등록
  → 워커가 메시지를 가져감
  → 실제 작업 실행
  → 성공 또는 재시도·실패 처리
```

API 서버는 작업을 직접 끝낼 때까지 기다리지 않고, 신뢰할 수 있는 큐에 “무엇을 해야 하는지”를 기록합니다. 워커는 큐에서 메시지를 가져와 실제 작업을 수행합니다.

이 구조는 여러 장점이 있습니다.

- 사용자 요청 응답 시간을 줄인다.
- 오래 걸리는 작업을 별도 자원에서 처리할 수 있다.
- 일시적인 외부 서비스 실패에 재시도할 수 있다.
- 요청량이 갑자기 늘어도 작업을 완충할 수 있다.
- 작업 종류별로 처리량과 우선순위를 분리할 수 있다.

하지만 큐는 마법이 아닙니다. 큐를 도입하면 분산된 상태, 재시도, 중복 실행, 순서, 모니터링을 의도적으로 설계해야 합니다.

## 3. ‘최소 한 번 전달’은 중복 실행을 의미한다

많은 작업 큐는 메시지를 최소 한 번(at-least-once) 전달하는 방식을 사용합니다. 작업자가 처리 완료를 알리기 전에 장애가 나면 큐는 메시지를 다시 전달합니다.

예를 들어 이메일 발송 워커가 이메일 서비스를 호출한 직후 장애가 발생했다고 합시다. 실제 이메일은 발송됐지만 워커는 성공 처리를 기록하지 못했을 수 있습니다. 큐는 메시지를 다시 전달하고, 사용자는 같은 이메일을 두 번 받을 수 있습니다.

따라서 작업 처리자는 멱등적이어야 합니다. 같은 작업이 여러 번 실행되어도 최종 상태가 안전해야 합니다.

방법은 작업 종류에 따라 다릅니다.

- 고유한 작업 ID를 저장해 이미 처리한 작업을 무시한다.
- 외부 서비스의 멱등성 키를 사용한다.
- 데이터베이스 유니크 제약 조건을 둔다.
- 현재 상태를 확인한 뒤 필요한 경우에만 변경한다.
- 중복 발송 방지를 위한 전송 기록을 둔다.

“정확히 한 번 실행”을 보장하려 하기보다, 중복 실행을 안전하게 처리하는 설계가 현실적이고 중요합니다.

## 4. 재시도는 무조건 반복이 아니다

네트워크 오류, 일시적인 5xx 응답, 일시적 제한 초과는 재시도할 가치가 있습니다. 그러나 잘못된 이메일 주소, 권한 없음, 유효하지 않은 요청 형식은 반복해도 성공하지 않습니다.

따라서 오류를 분류해야 합니다.

- 재시도 가능: 네트워크 오류, 일시적 외부 API 장애, 제한 초과
- 재시도 불가: 검증 오류, 존재하지 않는 리소스, 권한 오류
- 보류 필요: 결제 상태 불명확, 외부 시스템 확인 필요

재시도 간격에는 지수 백오프를 사용합니다. 첫 실패 직후 반복적으로 요청하면 장애 중인 외부 서비스를 더 압박하고, 제한을 더 쉽게 초과합니다.

```text
1차 실패 → 1분 후 재시도
2차 실패 → 5분 후 재시도
3차 실패 → 30분 후 재시도
```

여러 작업이 동시에 재시도되지 않도록 약간의 무작위 지연을 추가하는 것도 도움이 됩니다.

## 5. 실패 작업을 묻어두지 않는다

정해진 횟수만큼 재시도해도 실패한 작업은 별도의 실패 큐 또는 DLQ(Dead Letter Queue)로 보냅니다. 이 단계는 작업을 포기한다는 뜻이 아니라, 자동 재시도가 더 이상 안전하지 않은 상태라는 뜻입니다.

실패 큐에는 다음 정보가 있어야 합니다.

- 작업 ID와 유형
- 원래 입력 데이터
- 시도 횟수
- 마지막 오류와 시각
- 관련 사용자 또는 리소스 ID
- 재처리 가능 여부

운영자는 실패 목록을 보고 원인을 수정한 뒤 재처리할 수 있어야 합니다. 단, 재처리 버튼도 멱등성과 권한 검사를 고려해야 합니다.

## 6. 데이터베이스 저장과 큐 등록을 함께 생각한다

주문을 DB에 저장한 뒤 알림 작업을 큐에 넣는다고 해 봅시다. DB 저장은 성공했지만 큐 등록 전에 서버가 죽으면 주문은 생겼는데 알림은 발송되지 않습니다. 반대로 큐 등록은 됐지만 DB 트랜잭션이 실패하면 존재하지 않는 주문에 대한 알림 작업이 실행될 수 있습니다.

이런 불일치를 줄이는 대표적 방법이 아웃박스 패턴입니다.

1. 비즈니스 데이터와 이벤트 기록을 같은 DB 트랜잭션으로 저장한다.
2. 별도 프로세스가 이벤트 기록을 읽어 큐 또는 외부 서비스로 전달한다.
3. 전달 성공 여부를 기록하고, 실패하면 재시도한다.

이 방식은 “DB 저장”과 “외부 메시지 전송”을 하나의 원자적 작업처럼 다루기 어렵다는 현실을 관리합니다. 모든 서비스에 처음부터 필요한 것은 아니지만, 주문·결제·알림처럼 유실 비용이 큰 이벤트에서는 매우 유용합니다.

## 7. 작업 상태를 사용자에게 어떻게 보여 줄지 정한다

비동기 작업은 즉시 끝나지 않으므로 사용자 경험 설계가 필요합니다.

파일 내보내기를 예로 들면 다음 상태를 둘 수 있습니다.

```text
queued → processing → completed
                  ↘ failed
```

사용자에게 “다운로드 준비 중입니다”를 보여 주고, 완료되면 알림 또는 다운로드 링크를 제공할 수 있습니다. 중요한 것은 요청 성공을 작업 완료로 오해하게 하지 않는 것입니다.

API도 작업 자체의 상태를 표현해야 합니다.

```json
{
  "jobId": "job_123",
  "status": "queued"
}
```

클라이언트는 상태 조회, 서버 푸시, 알림을 통해 완료 여부를 알 수 있습니다. 민감한 작업이라면 작업 상태 조회 API에도 소유자와 조직 범위 검사가 필요합니다.

## 8. 순서와 동시성은 별도 요구사항이다

큐에 넣었다고 메시지 순서가 항상 보장되는 것은 아닙니다. 여러 워커가 병렬로 처리하면 나중 작업이 먼저 끝날 수 있습니다.

예를 들어 “회원 생성”과 “회원 환영 메시지 발송”은 순서가 중요할 수 있습니다. 반면 서로 무관한 이미지 처리 작업은 병렬 처리하는 편이 좋습니다.

순서가 필요한 작업은 같은 키를 가진 메시지를 순차 처리하거나, 이전 작업 완료 여부를 확인하거나, 상태 전이 검증으로 잘못된 순서를 막아야 합니다. 무작정 워커 수를 늘리는 것은 처리량을 높일 수 있지만 순서 문제와 외부 서비스 제한을 만들 수 있습니다.

## 9. 관측 가능성이 있어야 운영할 수 있다

큐 기반 구조는 요청이 끝난 뒤에도 작업이 계속되므로, 로그만으로는 현재 상태를 이해하기 어려울 수 있습니다.

최소한 다음을 관찰해야 합니다.

- 대기 중인 작업 수
- 작업 유형별 처리 시간
- 성공률과 재시도 횟수
- 실패 큐에 쌓인 작업 수
- 가장 오래 기다린 작업의 시간
- 워커 수와 처리량
- 외부 서비스 오류율
- 작업 ID와 원래 사용자 요청 ID의 연결

작업량이 계속 쌓이면 처리자가 부족하거나 외부 서비스가 느리거나 특정 작업이 멈췄을 수 있습니다. 큐 길이는 단순한 숫자가 아니라 시스템의 압력을 보여 주는 신호입니다.

## 오늘의 점검 질문

- 이 작업이 요청 성공 전에 반드시 끝나야 하는가?
- 같은 작업이 두 번 실행돼도 안전한가?
- 어떤 오류만 재시도해야 하는가?
- 반복 실패한 작업은 어디에서 확인하고 재처리하는가?
- DB 저장과 큐 등록 사이의 유실 가능성을 어떻게 줄이는가?
- 사용자는 비동기 작업의 진행 상태와 실패를 알 수 있는가?
- 순서가 필요한 작업과 병렬 처리할 작업을 구분했는가?
- 큐 적체와 실패를 운영 중에 감지할 수 있는가?

작업 큐의 목적은 단순히 요청을 비동기로 바꾸는 데 있지 않습니다. 느린 작업과 불확실한 외부 의존성을 사용자 요청에서 분리하고, 실패·재시도·중복 실행을 통제 가능한 운영 흐름으로 바꾸는 데 있습니다.

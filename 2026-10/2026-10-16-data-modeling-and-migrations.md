# 데이터 모델링과 마이그레이션: 기능보다 오래가는 구조 만들기

데이터 모델은 화면보다 오래 남습니다. 화면 구성, 버튼 문구, API 형태는 비교적 자주 바뀌지만 데이터베이스에 저장된 데이터는 사용자와 서비스의 기록으로 남습니다. 따라서 테이블 하나와 열 하나를 추가하는 일도 단순한 구현 세부 사항이 아니라, 제품의 규칙을 코드로 표현하는 설계 작업입니다.

좋은 데이터 모델의 목표는 정규화된 ERD를 만드는 데만 있지 않습니다. 데이터가 어떤 의미를 갖는지, 누가 어떤 범위에서 접근하는지, 시간이 지나도 어떻게 변경할 수 있는지, 오류가 생겨도 어떻게 복구할지를 함께 결정하는 데 있습니다.

## 1. 데이터의 의미부터 정의한다

테이블을 만들기 전에 “무엇을 저장할까?”보다 먼저 “이 값이 무엇을 뜻하는가?”를 문장으로 적어 보는 편이 좋습니다.

예를 들어 회원의 상태를 저장한다고 할 때, status가 정확히 무엇을 뜻하는지 결정해야 합니다.

- 가입 신청 상태인가?
- 교회 공동체 활동 상태인가?
- 관리자 검토 상태인가?
- 탈퇴 여부를 포함하는가?
- 일시 정지와 삭제는 구분하는가?

이 질문에 답하지 않은 채 문자열 하나로 상태를 저장하면 나중에 active, inactive, pending, deleted 같은 값이 뒤섞이고 각 화면이 서로 다른 의미로 해석할 수 있습니다.

상태값은 가능한 한 명확한 전이 규칙을 갖는 편이 좋습니다.

```text
pending → active → suspended
                 ↘ withdrawn
```

어떤 상태에서 어떤 상태로 바뀔 수 있는지, 누가 바꿀 수 있는지, 변경 이력이 필요한지까지 정하면 백엔드 검증과 프론트엔드 UI도 자연스럽게 정리됩니다.

## 2. 엔터티와 관계를 구분한다

사용자, 교회, 소그룹, 게시글, 댓글처럼 독립적으로 존재하는 대상을 엔터티라고 합니다. 이 엔터티들이 어떻게 연결되는지가 관계입니다.

예를 들어 한 교회에 여러 회원이 있고, 한 회원은 여러 소그룹에 참여할 수 있으며, 한 소그룹에도 여러 회원이 속할 수 있습니다. 이때 회원 테이블에 group_id 하나만 두면 한 회원이 여러 그룹에 속하는 경우를 표현할 수 없습니다.

다대다 관계에는 연결 테이블을 둡니다.

```text
members
groups
group_members
  - member_id
  - group_id
  - role
  - joined_at
```

연결 테이블은 단순한 중간 테이블이 아닙니다. 가입일, 그룹 내 역할, 참여 상태처럼 “관계 자체의 정보”를 담는 중요한 모델이 될 수 있습니다.

관계를 설계할 때는 다음을 점검합니다.

- 한쪽이 삭제되면 관계 데이터는 어떻게 되는가?
- 같은 관계가 중복 생성될 수 있는가?
- 관계에 별도 속성이 필요한가?
- 과거 관계 이력을 보관해야 하는가?
- 조직 또는 테넌트 경계가 필요한가?

## 3. 식별자와 유니크 제약 조건

각 행에는 보통 변경되지 않는 식별자가 필요합니다. 이메일이나 이름은 바뀔 수 있고 중복될 수 있으므로 내부 식별자로 적합하지 않을 수 있습니다. UUID나 데이터베이스가 생성하는 ID를 사용하면 외부 표현과 내부 식별을 분리할 수 있습니다.

중복되면 안 되는 비즈니스 규칙은 애플리케이션 코드뿐 아니라 데이터베이스 제약 조건으로도 표현해야 합니다.

예를 들면 다음과 같습니다.

- 한 교회 안에서 이메일은 중복될 수 없다.
- 한 회원은 같은 소그룹에 한 번만 참여할 수 있다.
- 외부 결제 거래 ID는 한 번만 저장할 수 있다.
- 멱등성 키는 같은 범위에서 한 번만 사용할 수 있다.

“먼저 조회하고 없으면 생성”하는 코드만으로는 동시 요청을 막지 못합니다. 두 요청이 거의 동시에 들어오면 둘 다 아직 없다고 판단할 수 있기 때문입니다. 유니크 제약 조건은 데이터베이스 차원의 마지막 방어선입니다.

## 4. null, 빈 문자열, 기본값의 의미를 정한다

데이터 모델에서 혼란을 일으키는 대표적인 원인은 null의 의미가 불명확한 경우입니다.

생년월일이 null이라면 다음 중 무엇일까요?

- 사용자가 입력하지 않았다.
- 입력 권한이 없어서 볼 수 없다.
- 데이터 이전 과정에서 누락되었다.
- 해당 개념이 적용되지 않는다.

서로 다른 의미를 모두 null로 표현하면 조회와 통계, 화면 표현이 복잡해집니다. 필요한 경우에는 상태 필드, 공개 범위 필드, 검증 결과 필드처럼 의미를 분리해야 합니다.

기본값도 신중해야 합니다. false, 0, 빈 문자열을 기본값으로 두면 “명시적으로 아니오를 선택했다”와 “아직 값을 입력하지 않았다”를 구분할 수 없을 수 있습니다.

## 5. 정규화와 비정규화의 균형

정규화는 중복을 줄이고 데이터 갱신 문제를 방지합니다. 회원 이름을 여러 테이블에 중복 저장하면 이름 변경 때 모든 위치를 갱신해야 하며, 일부만 바뀌면 데이터가 어긋납니다.

하지만 조회 성능이나 읽기 모델의 단순화를 위해 일부 데이터를 의도적으로 중복할 수도 있습니다. 이를 비정규화라고 합니다. 예를 들어 게시글 목록에 작성자 이름과 프로필 이미지 URL을 함께 저장하면 목록 조회는 빠를 수 있지만, 작성자 정보 변경 시 동기화 정책이 필요합니다.

비정규화는 성능 문제를 측정한 뒤 적용하는 것이 좋습니다. 먼저 정규화된 모델로 정확성을 확보하고, 실제 병목이 확인되었을 때 캐시, 집계 테이블, 읽기 전용 요약 데이터 등을 검토합니다.

## 6. 삭제는 단순하지 않다

DELETE 요청이 왔다고 항상 행을 즉시 물리적으로 지워야 하는 것은 아닙니다. 사용자에게는 삭제된 것처럼 보이지만, 감사·복구·법적 보존·관계 정합성을 위해 일정 기간 데이터를 보관해야 할 수 있습니다.

대표적인 방식은 소프트 삭제입니다.

```text
deleted_at = null      → 활성 데이터
deleted_at = timestamp → 삭제된 데이터
```

소프트 삭제를 쓴다면 모든 조회에서 삭제된 행을 제외하는 규칙, 관리자 복구 기능, 유니크 제약 조건과의 관계, 오래된 데이터를 실제 삭제하는 보존 정책까지 함께 설계해야 합니다.

반대로 민감 데이터처럼 실제 삭제가 필요하다면 연결된 데이터와 로그, 백업 보존 정책을 포함해 삭제 범위를 명확히 해야 합니다.

## 7. 마이그레이션은 배포 계획이다

마이그레이션은 스키마 변경 기록입니다. 테이블이나 열을 바꾸는 SQL 파일이지만, 운영 데이터가 있는 환경에서는 배포 계획 그 자체입니다.

안전한 마이그레이션은 대체로 다음 성질을 가집니다.

- 변경 목적이 명확하다.
- 적용 순서가 보장된다.
- 대용량 데이터에 과도한 잠금을 만들지 않는다.
- 기존 애플리케이션 버전과 일정 기간 호환된다.
- 실패 시 복구 방법을 고려한다.
- 테스트·스테이징 환경에서 먼저 검증된다.

예를 들어 기존 필드 이름을 바로 바꾸는 대신 점진적으로 전환할 수 있습니다.

1. 새 필드를 추가한다.
2. 새 코드가 두 필드를 함께 다루도록 배포한다.
3. 기존 데이터를 새 필드로 채운다.
4. 읽는 쪽을 새 필드로 전환한다.
5. 충분한 기간 뒤 이전 필드를 제거한다.

이 방식은 배포 중 서로 다른 앱 버전이 동시에 실행되는 상황에서도 위험을 줄입니다.

## 8. 데이터 이전은 재실행 가능해야 한다

데이터를 대량으로 수정하거나 새 구조로 옮기는 작업은 한 번에 끝나지 않을 수 있습니다. 중간에 실패하거나, 재배포하거나, 일부 데이터가 다시 처리될 수 있습니다.

따라서 데이터 이전 스크립트는 가능하면 멱등적으로 만듭니다. 같은 작업을 다시 실행해도 중복 데이터를 만들거나 이미 변환한 값을 망가뜨리지 않아야 합니다.

대량 작업에서는 다음도 고려합니다.

- 작은 배치로 나누기
- 진행 상황 기록
- 실패 항목 분리
- 재시도 정책
- 작업 중 들어오는 새 데이터 처리
- 이전 전후 검증 쿼리
- 롤백 또는 보정 계획

## 9. 인덱스와 쿼리 패턴을 함께 설계한다

인덱스는 데이터 모델 마지막 단계에 붙이는 장식이 아닙니다. 실제로 어떤 조건으로 조회하고, 어떻게 정렬하고, 어떤 테이블을 조인하는지를 바탕으로 설계해야 합니다.

예를 들어 교회별 활성 회원을 최근 가입 순으로 자주 조회한다면, church_id, status, created_at과 관련된 쿼리 패턴을 고려해야 합니다. 무작정 모든 열에 인덱스를 만들면 쓰기 비용과 저장 공간이 늘어납니다.

인덱스는 실행 계획과 느린 쿼리 로그를 통해 검증합니다. 작은 개발 데이터에서는 빨라 보이던 쿼리가 운영 데이터 크기에서 느려질 수 있다는 점을 기억해야 합니다.

## 10. 권한과 테넌트 경계는 모델에 포함한다

여러 조직의 데이터를 다루는 서비스에서는 organization_id, church_id 같은 테넌트 경계가 단순한 편의 필드가 아닙니다. 모든 주요 데이터에 일관되게 연결되어야 하고, API 필터와 행 단위 보안 정책도 같은 경계를 기준으로 동작해야 합니다.

권한은 별도 테이블이나 관계로 명시하는 편이 좋습니다. 역할 값을 사용자 행 하나에만 두면 조직별 역할, 그룹별 역할, 임시 권한을 표현하기 어려워질 수 있습니다.

## 오늘의 점검 질문

- 이 데이터와 상태값은 한 문장으로 명확히 설명되는가?
- 관계 자체에 저장해야 할 정보가 있는가?
- 중복되면 안 되는 규칙이 데이터베이스 제약 조건으로도 보장되는가?
- null, 기본값, 삭제 상태의 의미가 분명한가?
- 현재와 이전 앱 버전이 함께 실행돼도 마이그레이션이 안전한가?
- 대량 데이터 이전은 재실행과 실패 복구가 가능한가?
- 조회 패턴과 인덱스가 실제 데이터 크기에서 검증되었는가?
- 조직과 권한의 경계가 모델·API·보안 정책에 일관되게 반영되는가?

데이터 모델은 기능 구현을 빠르게 시작하게 하는 구조가 아니라, 기능이 늘어도 서비스가 무너지지 않게 하는 구조입니다. 작은 스키마 변경도 데이터의 의미, 운영 데이터, 권한, 배포 순서까지 함께 생각할 때 오래가는 시스템을 만들 수 있습니다.

# WebSocket과 SSE: 실시간 통신을 고르는 기준

예상 읽기 시간: 약 10~15분

알림, 채팅, 협업 편집, 주가 화면처럼 서버의 변화를 사용자가 새로고침하지 않아도 보여 주려면 실시간 통신이 필요합니다. 그렇다고 모든 기능에 WebSocket을 붙이는 것은 좋은 선택이 아닙니다. 데이터가 어느 방향으로 흐르는지, 연결이 끊겼을 때 무엇을 복구해야 하는지부터 정해야 합니다.

## 1. 폴링부터 이해하기

가장 단순한 방법은 일정 간격으로 API를 호출하는 폴링입니다.

~~~
GET /api/notifications
~~~

5초마다 호출하면 구현은 쉽지만, 변화가 없어도 요청이 계속 발생합니다. 반대로 간격을 길게 하면 최신 정보가 늦게 보입니다. 데이터 변화가 드물고 즉시성이 중요하지 않다면 폴링은 여전히 합리적인 선택입니다.

## 2. SSE는 서버에서 브라우저로 흐른다

Server-Sent Events(SSE)는 서버가 HTTP 연결을 유지하며 브라우저에 이벤트를 계속 보내는 방식입니다.

~~~
Content-Type: text/event-stream

event: notification
data: {"id":"n1","message":"새 댓글"}
~~~

브라우저에서는 EventSource로 받을 수 있습니다.

~~~
const stream = new EventSource("/api/events");
stream.addEventListener("notification", onNotification);
~~~

SSE는 서버에서 클라이언트로의 단방향 알림, 진행 상황, 대시보드 업데이트에 적합합니다. 브라우저의 자동 재연결 지원도 장점입니다.

하지만 클라이언트가 서버에 자주 메시지를 보내야 하는 채팅, 게임, 협업 편집에는 맞지 않을 수 있습니다. SSE 연결은 장시간 유지되므로 프록시의 타임아웃, 버퍼링, 로드 밸런서 설정도 확인해야 합니다.

## 3. WebSocket은 양방향 통신이다

WebSocket은 HTTP 핸드셰이크 뒤 별도 양방향 연결을 엽니다.

~~~
const socket = new WebSocket("wss://api.example.com/chat");

socket.addEventListener("open", () => {
  socket.send(JSON.stringify({ type: "join", roomId: "a" }));
});
~~~

서버와 클라이언트는 각각 언제든 메시지를 보낼 수 있습니다. 채팅, 실시간 공동 작업, 멀티플레이 기능처럼 클라이언트 이벤트가 빈번하고 낮은 지연이 중요한 기능에 적합합니다.

그러나 연결을 열었다고 해서 인증·인가가 해결되는 것은 아닙니다. 연결 시점뿐 아니라 방 참여, 메시지 발행 같은 각 작업에도 권한 검증이 필요합니다.

## 4. 재연결은 기능의 일부다

모바일 네트워크 전환, 노트북 절전, 서버 배포, 프록시 시간 제한 때문에 연결은 언제든 끊깁니다. 따라서 정상 연결만 구현한 실시간 기능은 운영에서 쉽게 깨집니다.

재연결 시에는 다음을 정의해야 합니다.

1. 지수 백오프와 지터로 재연결 폭주를 막는다.
2. 재연결 뒤 현재 상태를 다시 조회한다.
3. 마지막으로 처리한 이벤트 ID를 저장해 누락된 이벤트를 요청한다.
4. 같은 이벤트를 다시 받아도 안전하도록 중복 처리를 막는다.
5. 인증 토큰이 만료됐으면 갱신 후 연결한다.

“메시지를 받았다”와 “화면 상태가 최신이다”는 다릅니다. 이벤트는 변경을 알려 주는 힌트로 쓰고, 필요하다면 REST API로 정합성 있는 최신 상태를 다시 가져오는 전략이 안전합니다.

## 5. 순서와 중복을 가정하지 말기

분산 환경에서 메시지는 중복되거나, 늦게 도착하거나, 연결 재개 후 다시 전달될 수 있습니다. 서버가 각 이벤트에 단조 증가하는 ID나 버전을 부여하면 클라이언트가 순서를 판단할 수 있습니다.

~~~
{ "eventId": 1042, "type": "message.created", "payload": { ... } }
~~~

클라이언트는 이미 처리한 eventId를 무시하고, 예상보다 큰 번호가 오면 누락 여부를 확인할 수 있습니다. 백엔드도 메시지 브로커의 전달 보장과 데이터베이스 저장을 분리해 생각해야 합니다. “최소 한 번 전달”은 중복 처리 가능성을 의미합니다.

## 6. 확장과 운영

한 서버 인스턴스의 메모리에 연결과 방 정보를만 저장하면 여러 인스턴스로 확장할 때 문제가 생깁니다. 사용자가 A 서버에 연결돼 있는데 메시지는 B 서버에서 발생할 수 있기 때문입니다.

보통 Redis Pub/Sub, 메시지 브로커, 관리형 실시간 서비스 등을 이용해 인스턴스 간 이벤트를 전달합니다. 연결 수, 재연결 수, 메시지 지연, 드롭률, 방별 팬아웃 수를 관측해야 장애 원인을 찾을 수 있습니다.

또한 오래 유지되는 연결은 일반 HTTP 요청과 다른 용량 계획이 필요합니다. 파일 디스크립터, 메모리, 로드 밸런서의 최대 연결 수와 유휴 타임아웃을 함께 점검하세요.

## 선택 기준

- 변화가 드물고 즉시성이 낮다: 폴링
- 서버에서 사용자에게 알림만 보낸다: SSE
- 양방향 메시지와 낮은 지연이 중요하다: WebSocket
- 강한 데이터 정합성이 필요하다: 실시간 이벤트와 재조회 API를 함께 사용

## 마무리

실시간 기능의 핵심은 연결 기술 자체보다 끊김 뒤의 복구입니다. WebSocket은 강력하지만 운영 복잡도가 높고, SSE는 단방향 알림에 간결합니다. 어떤 방식을 택하든 인증, 재연결, 중복·누락 이벤트, 관측 지표까지 포함해 설계해야 합니다.

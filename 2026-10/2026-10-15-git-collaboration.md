# Git 협업과 변경 관리

Git은 단순한 백업 도구가 아닙니다. 코드가 왜, 언제, 어떤 의도로 바뀌었는지를 남기고 여러 사람이 안전하게 작업하도록 돕는 변경 관리 도구입니다. 프론트엔드와 백엔드가 같은 제품을 함께 만들수록 브랜치, 커밋, 코드 리뷰, 배포 흐름의 규칙이 중요해집니다.

## 커밋은 작은 작업 단위여야 한다

좋은 커밋은 하나의 의도를 담습니다. “회원 목록의 페이지네이션을 추가한다”, “권한 검사 누락을 수정한다”, “API 오류 형식을 통일한다”처럼 나중에 읽었을 때 변경 이유를 이해할 수 있어야 합니다.

서로 무관한 포맷팅, 리팩터링, 기능 추가, 버그 수정을 하나의 커밋에 섞으면 리뷰와 롤백이 어려워집니다. 기능을 완료하지 못했더라도 의미 있는 중간 단계가 있다면 작은 커밋으로 나누는 편이 좋습니다.

커밋 메시지는 변경의 결과보다 의도를 설명합니다.

- 좋음: `fix: prevent duplicate order creation`
- 좋음: `feat: add cursor pagination to member list`
- 아쉬움: `update`
- 아쉬움: `fix bug`

## 브랜치는 격리된 작업 공간이다

기본 브랜치(main 또는 master)는 언제든 배포 가능한 상태를 유지하는 것이 이상적입니다. 기능, 버그 수정, 실험은 별도 브랜치에서 진행합니다.

```text
main
 ├─ feat/member-pagination
 ├─ fix/duplicate-payment
 └─ chore/update-dependencies
```

브랜치 이름은 작업 목적이 보이게 짓습니다. 너무 오래 살아 있는 대형 브랜치는 본 브랜치와 차이가 커져 병합 충돌과 리뷰 비용이 증가합니다. 기능을 가능한 작은 단위로 나누고 자주 통합하는 편이 좋습니다.

## Pull Request는 병합 요청이 아니라 대화 기록이다

PR에는 무엇을 바꿨는지, 왜 바꿨는지, 어떤 위험이 있는지, 어떻게 검증했는지를 적습니다. 리뷰어가 코드를 처음 읽는 상황을 가정하면 좋습니다.

좋은 PR 설명에는 다음이 포함됩니다.

- 변경 목적과 배경
- 주요 변경 사항
- 사용자에게 보이는 변화
- 테스트와 검증 결과
- 알려진 제한 또는 후속 작업
- 화면 변경이 있다면 이미지나 영상

리뷰는 스타일 지적만 하는 시간이 아닙니다. 권한 누락, 예외 처리, 데이터 정합성, 성능, API 계약 변경, 테스트 누락을 함께 찾는 설계 검토 과정입니다.

## 병합 충돌은 코드보다 의도를 먼저 확인한다

병합 충돌이 발생하면 Git이 두 변경 중 어느 것을 선택할지 모르겠다는 뜻입니다. 단순히 충돌 표시를 지우는 것으로 끝내면 한쪽 기능을 실수로 제거할 수 있습니다.

충돌을 해결할 때는 다음 순서가 안전합니다.

1. 두 변경이 각각 무엇을 의도했는지 이해한다.
2. 어느 쪽이 최신 요구사항인지 확인한다.
3. 필요한 변경을 모두 반영한다.
4. 빌드·테스트·실행으로 결과를 확인한다.
5. 충돌 해결 커밋을 작고 명확하게 남긴다.

자동 병합이 성공해도 의미 충돌은 남을 수 있습니다. 같은 화면의 상태 관리 방식을 서로 다르게 바꾸거나, API 응답의 의미를 다르게 가정한 변경은 컴파일 오류 없이도 문제를 만들 수 있습니다.

## 히스토리 수정과 공유 브랜치

이미 원격에 공유된 브랜치의 히스토리를 무심코 다시 쓰면 다른 사람의 작업을 방해할 수 있습니다. rebase나 force push는 개인 작업 브랜치에서는 유용할 수 있지만, 협업 브랜치에서는 팀 규칙과 충분한 확인이 필요합니다.

특히 기본 브랜치에는 보호 규칙을 두는 것이 좋습니다.

- 직접 push 제한
- PR 리뷰 승인 요구
- 자동 테스트 통과 요구
- 최신 기본 브랜치와의 동기화 요구
- force push 제한

## 배포와 롤백을 연결한다

좋은 변경 관리에는 “배포 방법”뿐 아니라 “문제가 생기면 어떻게 되돌릴지”도 포함됩니다. 데이터베이스 마이그레이션, API 변경, 기능 플래그는 롤백 가능성을 고려해야 합니다.

예를 들어 새 API 필드를 추가한 뒤 앱이 이를 사용하게 하고, 충분히 전환된 뒤 이전 필드를 제거하는 점진적 변경은 한 번에 이름을 바꾸는 것보다 안전합니다. 기능 플래그는 코드 배포와 기능 공개를 분리해 위험을 줄일 수 있습니다.

## 오늘의 점검 질문

- 한 커밋이 한 가지 명확한 의도를 담는가?
- 기본 브랜치가 배포 가능한 상태를 유지하는가?
- PR 설명에 검증 방법과 위험이 남아 있는가?
- 충돌 해결 뒤 실제 동작을 확인하는가?
- 공유 브랜치의 히스토리를 안전하게 다루는가?
- 배포 후 문제 발생 시 롤백 또는 기능 비활성화 방법이 있는가?

Git 흐름의 목적은 복잡한 절차를 늘리는 데 있지 않습니다. 팀이 변경의 의도를 공유하고, 위험한 변경을 검토하며, 문제가 생겼을 때 빠르게 이해하고 복구하도록 돕는 데 있습니다.

# JavaScript 이벤트 루프: 비동기 코드가 실행되는 순서와 성능

JavaScript 코드를 읽다 보면 위에서 아래로 작성했는데 출력 순서가 예상과 다를 때가 있습니다. API 호출을 동시에 시작했는데 화면은 멈추거나, 서버가 비동기 요청을 처리하면서도 갑자기 느려지는 경우도 있습니다.

이런 현상을 이해하는 핵심이 이벤트 루프입니다. 이벤트 루프는 프론트엔드의 버튼 클릭·화면 갱신과 백엔드의 파일·네트워크 처리 모두에 영향을 줍니다. 다만 브라우저와 Node.js는 서로 다른 실행 환경이므로, 비슷한 원리를 공유하더라도 세부 일정은 동일하다고 가정하면 안 됩니다.

## 1. JavaScript와 실행 환경을 구분한다

JavaScript 엔진은 언어의 코드를 실행합니다. 브라우저나 Node.js는 엔진을 둘러싼 실행 환경으로서 타이머, 네트워크, 파일 접근과 같은 기능을 제공합니다.

하나의 일반적인 JavaScript 실행 스레드에서는 한 번에 하나의 코드 흐름을 실행합니다. 함수가 호출되면 호출 스택에 쌓이고, 함수가 끝나면 스택에서 빠집니다. 현재 실행 중인 작업은 보통 중간에 다른 JavaScript 작업이 끼어들지 않고 끝까지 실행됩니다. 이를 run-to-completion이라고 합니다.

하지만 애플리케이션 전체가 반드시 하나의 스레드만 사용한다는 뜻은 아닙니다. 브라우저의 Web Worker나 Node.js의 worker_threads는 별도 실행 스레드를 사용할 수 있고, 실행 환경은 네트워크와 파일 I/O를 별도의 운영체제 기능이나 작업자 풀에 맡길 수 있습니다.

중요한 구분은 이렇습니다. 비동기 API가 기다리는 동안 다른 작업을 진행할 수 있다는 것과, 현재 스레드에서 CPU 연산을 여러 개 동시에 실행한다는 것은 다릅니다.

## 2. 호출 스택과 대기 중인 작업

예제를 살펴보겠습니다.

```js
console.log("A");

setTimeout(() => {
  console.log("B");
}, 0);

console.log("C");
```

결과는 A, C, B 순서입니다. 타이머는 콜백을 즉시 실행하지 않습니다. 현재 동기 코드가 끝난 뒤 해당 콜백이 실행될 수 있는 상태가 되며, 다른 작업이나 실행 환경의 스케줄링에 따라 더 늦어질 수도 있습니다.

setTimeout의 숫자는 정확한 실행 시각이 아니라 콜백이 실행되기까지의 최소 지연 조건에 가깝습니다. 0ms라고 해서 현재 실행 중인 코드를 중단하고 즉시 실행하는 것은 아닙니다.

## 3. 태스크와 마이크로태스크

브라우저에서는 클릭 이벤트, 타이머 콜백 같은 일반 태스크와 Promise 반응 콜백 같은 마이크로태스크를 구분해 이해하면 도움이 됩니다.

```js
console.log("1");

setTimeout(() => console.log("2"), 0);
Promise.resolve().then(() => console.log("3"));

console.log("4");
```

이 코드의 출력은 1, 4, 3, 2입니다.

1. 동기 코드가 1을 출력합니다.
2. 타이머 콜백을 예약합니다.
3. Promise의 then 콜백을 마이크로태스크로 예약합니다.
4. 동기 코드가 4를 출력합니다.
5. 현재 스택이 비워진 뒤 마이크로태스크 3이 실행됩니다.
6. 이후 타이머 콜백 2가 실행됩니다.

마이크로태스크가 실행 중 새로운 마이크로태스크를 계속 추가하면 다음 태스크나 렌더링 기회가 지연될 수 있습니다. 그러므로 마이크로태스크를 무제한으로 반복 예약하는 방식은 피해야 합니다.

이 설명은 예제의 일반적인 브라우저 실행 흐름을 이해하기 위한 모델입니다. 모든 비동기 API의 완료 순서나 브라우저의 실제 렌더링 시점을 단순한 하나의 큐로 예측해서는 안 됩니다.

## 4. async/await는 비동기 작업을 쉽게 읽게 한다

async/await는 Promise 기반 코드를 동기 코드처럼 읽기 쉽게 만들어 줍니다.

```js
async function loadProfile() {
  console.log("요청 전");
  const response = await fetch("/api/me");
  console.log("응답 후");
  return response.json();
}

loadProfile();
console.log("다른 작업");
```

fetch가 끝나기를 기다리는 동안 현재 함수의 나머지 부분은 나중으로 미뤄집니다. 따라서 일반적으로 “요청 전”, “다른 작업”, “응답 후” 순서로 출력됩니다. await가 스레드 전체를 멈추는 것이 아닙니다.

그러나 await 앞이나 뒤에서 무거운 동기 계산을 실행하면 그 계산은 여전히 현재 스레드를 점유합니다. async라는 키워드 자체가 CPU 작업을 다른 스레드로 옮겨 주지는 않습니다.

## 5. 직렬 실행과 동시 시작을 구분한다

두 요청이 서로 독립적인데 순서대로 기다리면 불필요한 대기가 생길 수 있습니다.

```js
const profile = await fetchProfile();
const posts = await fetchPosts();
```

위 코드는 프로필을 받은 뒤 게시글 요청을 시작합니다. 게시글 요청이 프로필 결과에 의존하지 않는다면 두 요청을 먼저 시작할 수 있습니다.

```js
const [profile, posts] = await Promise.all([
  fetchProfile(),
  fetchPosts(),
]);
```

Promise.all은 모든 작업이 성공하면 결과를 배열로 돌려주고, 하나라도 거부되면 전체 Promise가 거부됩니다. 개별 작업의 성공과 실패를 모두 확인해야 한다면 Promise.allSettled를 고려할 수 있습니다.

단, Promise.all은 마법처럼 CPU 연산을 병렬화하지 않습니다. 또한 요청을 수천 개 동시에 시작하면 서버·DB 연결·외부 API 제한을 압박할 수 있습니다. 필요하다면 동시 실행 수를 제한하고, 실패·취소·재시도 정책을 함께 설계해야 합니다.

## 6. 오래 걸리는 동기 작업은 화면과 서버를 멈추게 한다

브라우저 메인 스레드에서 큰 배열을 오랫동안 정렬하거나, 대용량 JSON을 한 번에 처리하거나, 복잡한 암호화 연산을 수행하면 클릭과 스크롤, 화면 표시가 지연될 수 있습니다.

Node.js에서도 요청 처리 콜백이 오랫동안 CPU를 점유하면 같은 이벤트 루프에서 처리할 다른 요청이 기다리게 됩니다. 비동기 서버라고 해서 CPU 집약적 동기 코드가 자동으로 안전해지는 것은 아닙니다.

해결 방법은 작업의 성격에 따라 다릅니다.

- 데이터 양을 줄이거나 알고리즘을 개선한다.
- 긴 작업을 적절한 단위로 나누고 제어를 돌려준다.
- 브라우저에서는 Web Worker를 검토한다.
- Node.js에서는 worker_threads나 별도 작업 프로세스를 검토한다.
- 시간이 오래 걸리는 작업을 큐에 넣고 결과를 나중에 제공한다.

작업을 나눌 때도 마이크로태스크만 계속 예약하면 렌더링이나 다른 태스크가 밀릴 수 있습니다. 어떤 방식으로 제어를 돌려줄지는 실제 실행 환경에서 측정해야 합니다.

## 7. Node.js의 이벤트 루프는 브라우저와 다르다

Node.js는 내부적으로 여러 단계로 이벤트 루프를 운영하며, 타이머, I/O, setImmediate 같은 콜백을 처리합니다. Promise 마이크로태스크와 process.nextTick에도 별도 처리 규칙이 있습니다.

중요한 실무 원칙은 간단합니다. 브라우저에서 본 실행 순서를 Node.js의 모든 상황에 그대로 적용하지 말고, setTimeout과 setImmediate의 상대적 순서에 업무 로직의 정확성을 의존하지 마세요. 실행 위치와 런타임 버전에 따라 관찰 결과가 달라질 수 있습니다.

process.nextTick을 재귀적으로 지나치게 예약하면 I/O 진행이 지연될 수 있으므로 신중하게 사용해야 합니다. 세부 순서가 중요한 코드라면 공식 문서를 확인하고 실제 지원 버전에서 테스트하는 것이 좋습니다.

## 8. 비동기 코드에도 경쟁 상태가 생긴다

한 스레드에서 JavaScript 작업이 실행되더라도 await를 경계로 여러 요청이 번갈아 진행될 수 있습니다. 따라서 비동기 코드에는 경쟁 상태가 생길 수 있습니다.

예를 들어 검색창에 A를 입력한 뒤 곧바로 B를 입력했다고 합시다. A 요청이 늦게 끝나면 B 검색 결과를 표시한 뒤 A 결과로 화면이 덮일 수 있습니다.

대응 방법은 다음과 같습니다.

- 이전 요청을 AbortController로 취소한다.
- 요청마다 번호를 붙이고 최신 요청의 결과만 반영한다.
- 컴포넌트가 더 이상 필요 없는 결과를 무시한다.
- 서버의 중요한 쓰기 작업은 DB 제약 조건·트랜잭션·버전 검사로 보호한다.

클라이언트에서 요청을 취소했다고 서버의 처리가 반드시 취소되는 것은 아닙니다. 결제·주문처럼 중요한 작업은 서버 측 멱등성과 상태 확인이 여전히 필요합니다.

## 9. 오류와 취소를 설계한다

비동기 함수의 실패는 Promise 거부로 전달됩니다. await 주변에 try/catch를 두거나 호출자에게 오류를 전파해 적절히 처리해야 합니다.

```js
try {
  const profile = await fetchProfile();
  showProfile(profile);
} catch (error) {
  showError("프로필을 불러오지 못했습니다.");
}
```

실제 서비스에서는 오류를 모두 같은 메시지로 처리하기보다 인증 만료, 네트워크 실패, 권한 거부, 입력 오류, 취소를 구분해야 합니다. 사용자가 화면을 이동해 의도적으로 요청을 취소한 경우까지 일반 오류 알림으로 보여 주면 오히려 불편할 수 있습니다.

## 10. 성능은 추측하지 말고 측정한다

비동기 처리를 추가하기 전에 다음을 확인합니다.

- 작업이 실제로 네트워크·DB 대기인지, CPU 계산인지
- 메인 스레드 또는 이벤트 루프를 얼마나 오래 점유하는지
- 독립적인 요청이 불필요하게 직렬화돼 있는지
- 동시 요청이 외부 서비스 제한을 초과하지 않는지
- 취소·오류·늦은 응답이 화면 상태에 어떤 영향을 주는지

브라우저 개발자 도구의 성능 기록과 네트워크 탭, 서버의 응답 시간·이벤트 루프 지연·CPU 지표를 함께 보면 병목을 더 정확히 구분할 수 있습니다.

이벤트 루프는 암기 문제가 아니라, 사용자의 클릭과 서버 요청이 언제 처리되는지 이해하기 위한 모델입니다. 비동기 대기와 실제 병렬 계산을 구분하고, 작업의 실행 시간·순서·오류를 함께 설계하면 더 빠르고 예측 가능한 서비스를 만들 수 있습니다.

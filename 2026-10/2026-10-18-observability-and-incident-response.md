# 관측 가능성과 장애 대응: 문제가 생긴 뒤에도 시스템을 이해하는 법

운영 환경에서 문제는 반드시 생깁니다. 서버가 느려지고, 외부 결제 서비스가 실패하고, 특정 사용자만 오류를 겪고, 배포 직후 일부 기능이 깨질 수 있습니다. 중요한 것은 장애가 없다고 가정하는 것이 아니라, 문제가 생겼을 때 빠르게 감지하고 원인을 좁히며 안전하게 복구할 수 있도록 준비하는 일입니다.

관측 가능성(Observability)은 시스템 내부 상태를 로그, 지표, 추적 정보 같은 외부 신호로 이해할 수 있는 능력입니다. 단순히 로그를 많이 남기는 것이 아니라, “지금 무엇이 나쁜가?”, “어디서 느려졌는가?”, “어떤 요청이 실패했는가?”에 답할 수 있게 만드는 것입니다.

## 1. 모니터링과 관측 가능성의 차이

모니터링은 미리 정한 수치를 계속 보는 일에 가깝습니다. CPU가 80%를 넘었는지, 오류율이 5%를 넘었는지, 큐에 대기 중인 작업이 너무 많은지처럼 알려진 문제를 감지하는 데 유용합니다.

관측 가능성은 예상하지 못한 문제를 조사할 수 있는 능력입니다. “특정 지역의 모바일 사용자만 저장에 실패한다”, “관리자 화면에서만 요청이 느리다”, “배포 뒤 p95 응답 시간이 증가했다” 같은 질문에 답하려면 여러 신호를 연결할 수 있어야 합니다.

둘은 대체 관계가 아닙니다. 모니터링은 빠른 경보를 제공하고, 관측 가능성은 경보가 울린 뒤 원인을 찾게 해 줍니다.

## 2. 세 가지 핵심 신호: 로그, 지표, 추적

### 로그

로그는 특정 순간에 일어난 일을 기록합니다. 요청 경로, 상태 코드, 오류 메시지, 작업 ID, 처리 시간처럼 사건의 맥락을 담습니다.

좋은 로그는 구조화되어 있어야 합니다. 사람이 읽는 문장만 남기기보다 검색·집계 가능한 필드를 함께 둡니다.

```json
{
  "level": "error",
  "event": "payment_authorization_failed",
  "requestId": "req_abc123",
  "orderId": "order_456",
  "provider": "payment-service",
  "statusCode": 502,
  "durationMs": 1830
}
```

하지만 로그에는 비밀번호, 토큰, 전체 카드 번호, 주민번호, 민감한 개인정보를 남기면 안 됩니다. 문제를 조사할 수 있을 만큼 기록하되, 데이터 노출 위험은 최소화해야 합니다.

### 지표

지표는 시간이 흐르며 변하는 숫자입니다. 요청 수, 오류율, 응답 시간, CPU 사용량, DB 연결 수, 큐 길이 등이 대표적입니다.

서비스 품질을 볼 때 자주 확인하는 네 가지 신호가 있습니다.

- 트래픽: 초당 요청 수, 활성 사용자 수
- 오류: 4xx·5xx 비율, 실패 작업 수
- 지연 시간: 평균뿐 아니라 p95·p99 응답 시간
- 포화도: CPU, 메모리, DB 연결, 큐 적체

평균 응답 시간만 보면 일부 사용자의 나쁜 경험을 놓칠 수 있습니다. 평균이 200ms여도 p95가 3초라면 사용자 20명 중 1명은 3초 이상 기다릴 수 있습니다.

### 분산 추적

한 사용자의 요청이 API 서버, 데이터베이스, 캐시, 파일 저장소, 외부 결제 서비스, 큐 워커를 거친다면 로그만으로 전체 흐름을 연결하기 어렵습니다.

이때 요청마다 trace ID를 만들고 하위 작업에 전달합니다.

```text
브라우저 요청
  → API trace
    → DB query span
    → 외부 API span
    → 큐 작업 span
```

분산 추적은 느린 요청이 DB 때문인지, 외부 API 때문인지, 특정 내부 함수 때문인지 시간 축으로 보여 줍니다. 특히 여러 서비스가 연결된 환경에서 원인 분석 시간을 크게 줄여 줍니다.

## 3. 사용자 관점의 서비스 수준을 정한다

기술 지표는 사용자 경험과 연결되어야 합니다. “서버 CPU가 낮다”는 사실보다 “사용자가 회원 목록을 2초 안에 볼 수 있는가?”가 더 중요합니다.

서비스 수준 목표(SLO)를 정할 때는 사용자 행동을 기준으로 생각합니다.

- 로그인 요청의 99%가 2초 안에 완료된다.
- 회원 정보 저장 성공률이 99.9% 이상이다.
- 결제 승인 결과가 10초 안에 확인된다.
- 대량 내보내기 작업의 95%가 5분 안에 끝난다.

모든 기능에 지나치게 높은 목표를 잡으면 비용과 복잡도만 커질 수 있습니다. 결제와 권한 변경처럼 실패 비용이 큰 흐름에는 엄격한 목표가 필요하고, 통계 갱신처럼 약간 늦어도 되는 작업에는 다른 기준을 둘 수 있습니다.

## 4. 경보는 행동 가능한 문제에만 울린다

경보가 너무 많으면 사람들은 알림을 무시합니다. 이를 알림 피로라고 합니다. 반대로 경보가 너무 늦으면 사용자나 고객 지원이 먼저 장애를 발견합니다.

좋은 경보는 “누군가 지금 행동해야 하는가?”라는 질문에 답합니다.

예를 들어 CPU가 잠시 80%를 넘었다고 바로 경보를 울리기보다, 다음처럼 사용자 영향과 지속 시간을 함께 고려할 수 있습니다.

- 5xx 오류율이 5분 동안 기준을 넘음
- 결제 승인 실패율이 평소보다 급격히 증가
- 큐 대기 시간이 계속 증가
- 로그인 성공률이 서비스 목표 아래로 떨어짐
- 특정 중요 API의 p95 응답 시간이 오래 지속됨

경보 메시지에는 무엇이 나쁜지, 언제부터인지, 어디를 먼저 봐야 하는지, 관련 대시보드와 실행 절차가 무엇인지 포함하는 편이 좋습니다.

## 5. 장애 대응은 역할과 순서가 필요하다

장애가 발생하면 동시에 여러 사람이 추측과 수정을 시작하기 쉽습니다. 하지만 우선순위 없이 움직이면 사용자 영향은 커지고 원인 분석은 어려워집니다.

기본 대응 순서는 다음과 같습니다.

1. 감지: 실제 사용자 영향이 있는지 확인한다.
2. 분류: 어떤 기능, 사용자, 지역, 환경에 영향이 있는지 좁힌다.
3. 완화: 롤백, 기능 플래그 비활성화, 트래픽 제한, 대체 경로로 피해를 줄인다.
4. 조사: 로그·지표·추적으로 원인을 찾는다.
5. 복구: 안전한 수정 또는 설정 변경을 적용한다.
6. 검증: 오류율과 핵심 흐름이 정상으로 돌아왔는지 확인한다.
7. 회고: 원인, 대응, 재발 방지 조치를 기록한다.

중요한 원칙은 원인을 완전히 알기 전에라도 사용자 피해를 줄이는 완화 조치를 먼저 고려하는 것입니다. 새 배포가 원인으로 의심되면 빠른 롤백이 정답일 수 있습니다.

## 6. 롤백과 기능 플래그를 준비한다

배포를 되돌릴 수 있다는 사실은 장애 대응 시간을 크게 줄입니다. 하지만 데이터베이스 마이그레이션이 되돌릴 수 없는 형태이거나, 배포 뒤 데이터 형식이 바뀌었다면 코드만 이전 버전으로 돌려도 문제가 남을 수 있습니다.

따라서 변경을 점진적으로 설계해야 합니다.

- 새 필드를 먼저 추가하고 이전 필드를 바로 삭제하지 않는다.
- 새 코드가 이전·새 데이터 형식을 함께 읽을 수 있게 한다.
- 충분히 전환된 뒤 이전 구조를 제거한다.
- 위험한 새 기능은 기능 플래그 뒤에 둔다.
- 기능 플래그를 누가 언제 끌 수 있는지 정한다.

기능 플래그는 배포와 공개를 분리합니다. 문제가 생기면 전체 배포를 되돌리지 않고 특정 기능만 빠르게 끌 수 있습니다. 다만 오래된 플래그를 방치하면 코드가 복잡해지므로 소유자와 제거 시점을 관리해야 합니다.

## 7. 장애 중 커뮤니케이션도 제품 품질이다

사용자는 내부 원인을 알 필요는 없지만, 자신의 작업이 안전한지와 언제 다시 시도할 수 있는지는 알아야 합니다.

장애 안내는 사실 중심으로 짧고 명확해야 합니다.

- 어떤 기능에 문제가 있는가?
- 어떤 사용자가 영향을 받는가?
- 데이터 유실 또는 중복 가능성이 있는가?
- 사용자가 지금 해야 할 일은 무엇인가?
- 다음 업데이트는 언제 제공할 것인가?

“최대한 빨리 처리 중입니다”만 반복하기보다, 확인된 사실과 다음 안내 시점을 알려 주는 편이 신뢰를 만듭니다. 내부 채널에서도 담당자, 현재 영향, 완화 조치, 다음 확인 시점을 한곳에 기록하면 중복 작업을 줄일 수 있습니다.

## 8. 장애 회고는 비난이 아니라 시스템 개선이다

장애가 끝난 뒤 회고를 하지 않으면 같은 문제가 다시 나타날 가능성이 큽니다. 좋은 회고는 누가 실수했는지 찾는 문서가 아니라, 시스템과 절차가 왜 그 실수를 막지 못했는지 찾는 문서입니다.

회고에는 다음을 남길 수 있습니다.

- 발생 시각과 감지 시각
- 사용자 영향과 범위
- 시간순 대응 기록
- 직접 원인과 기여 요인
- 잘 작동한 부분
- 어려웠던 부분
- 재발 방지 작업과 담당자
- 검증 방법과 완료 기준

“주의한다”는 재발 방지책은 약합니다. 자동 테스트 추가, 알림 조건 개선, 권한 정책 강화, 롤백 절차 문서화, 대시보드 추가처럼 검증 가능한 조치가 필요합니다.

## 오늘의 점검 질문

- [ ] 중요 요청을 요청 ID로 끝까지 추적할 수 있는가?
- [ ] 평균뿐 아니라 p95·p99 지연 시간과 오류율을 보는가?
- [ ] 로그에 민감한 정보가 남지 않는가?
- [ ] 경보가 실제로 행동해야 하는 문제만 알려 주는가?
- [ ] 장애 시 먼저 완화할 방법이 있는가?
- [ ] 위험한 기능을 빠르게 비활성화할 수 있는가?
- [ ] 배포와 마이그레이션을 안전하게 롤백할 수 있는가?
- [ ] 장애 뒤 재발 방지 작업이 담당자와 완료 기준을 갖는가?

관측 가능성의 목표는 모든 문제를 없애는 것이 아닙니다. 문제가 생겼을 때 추측에 의존하지 않고, 사용자 피해를 줄이며, 시스템을 더 나은 방향으로 개선할 수 있게 만드는 것입니다.

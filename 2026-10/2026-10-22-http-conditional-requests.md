# HTTP 조건부 요청과 낙관적 동시성 제어

예상 읽기 시간: 약 10~15분

두 관리자가 같은 게시글을 수정하는 상황을 생각해 보겠습니다. 관리자 A와 B가 같은 버전의 글을 열고, A가 제목을 수정해 저장합니다. 잠시 후 B가 본문을 수정해 저장하면 어떻게 될까요?

서버가 B의 요청을 그대로 받아들이면 B가 열었던 **이전 버전**으로 A의 변경 사항이 덮어써질 수 있습니다. 이처럼 한 사용자의 변경이 다른 사용자의 저장 때문에 사라지는 문제를 *갱신 손실(lost update)*이라고 합니다.

오늘은 이 문제를 HTTP의 `ETag`와 `If-Match`를 이용해 감지하는 방법을 살펴보겠습니다. 프론트엔드는 충돌을 사용자에게 설명하고, 백엔드는 실제로 덮어쓰기를 막는 역할을 합니다.

## 1. 먼저 구분할 것: 최신 데이터와 내가 읽은 데이터

문제의 핵심은 사용자가 편집한 데이터와 서버의 현재 데이터가 다를 수 있다는 것입니다.

```text
시간    서버의 문서          관리자 A              관리자 B
1       버전 1              버전 1 읽기          버전 1 읽기
2       버전 2              수정 후 저장 성공
3       버전 3                                   이전 버전으로 저장
```

3번 시점에서 서버가 단순히 요청 본문을 저장하면 B가 A의 변경을 덮어쓸 수 있습니다. 이는 요청이 빠르게 들어오느냐보다, **어떤 버전을 기준으로 수정했느냐**의 문제입니다.

한 가지 접근은 사용자가 편집하는 동안 다른 사람의 수정을 잠그는 것입니다. 하지만 사용자가 브라우저를 닫거나 오래 자리를 비우는 경우 잠금의 만료와 해제를 관리해야 합니다.

오늘 살펴볼 **낙관적 동시성 제어**는 다르게 접근합니다.

1. 여러 사용자가 자유롭게 같은 데이터를 읽고 수정합니다.
2. 저장할 때 읽었던 버전이 여전히 최신인지 확인합니다.
3. 최신 버전이 아니라면 저장을 거부하고 충돌을 처리합니다.

충돌이 항상 발생하지는 않는다는 가정 아래, 저장 시점에 충돌을 확인하는 방식입니다.

## 2. `ETag`: 응답의 버전을 식별하는 값

서버는 리소스를 응답할 때 `ETag` 헤더를 제공할 수 있습니다.

```http
GET /api/articles/42 HTTP/1.1
Host: example.com
```

```http
HTTP/1.1 200 OK
Content-Type: application/json
ETag: "article-42-v7"

{
  "id": 42,
  "title": "이벤트 루프 이해하기",
  "content": "본문 내용"
}
```

`ETag`는 응답 표현의 버전을 식별하는 검증자입니다. 위의 `"article-42-v7"`은 설명을 위한 예시일 뿐, HTTP가 특정한 생성 방식을 강제하는 것은 아닙니다. 클라이언트는 값을 해석하려 하기보다 서버가 준 값을 그대로 보관하고 다시 전달하는 것이 안전합니다. [MDN: ETag](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/ETag)

예를 들어 프론트엔드는 본문과 함께 ETag도 보관할 수 있습니다.

```js
async function loadArticle(id) {
  const response = await fetch(`/api/articles/${id}`);

  if (!response.ok) {
    throw new Error(`불러오기 실패: ${response.status}`);
  }

  return {
    article: await response.json(),
    etag: response.headers.get("ETag"),
  };
}
```

다른 출처의 API를 호출하는 경우에는 브라우저가 JavaScript에 `ETag`를 노출하도록 서버의 CORS 응답 설정이 필요할 수 있습니다. 예를 들어 `Access-Control-Expose-Headers: ETag`를 설정합니다.

## 3. `If-Match`: 이 버전이 여전히 최신일 때만 저장하기

사용자가 편집한 뒤 저장할 때는 읽어 둔 ETag를 `If-Match` 헤더에 넣습니다.

```http
PUT /api/articles/42 HTTP/1.1
Content-Type: application/json
If-Match: "article-42-v7"

{
  "title": "이벤트 루프와 비동기 실행",
  "content": "수정한 본문"
}
```

서버는 현재 리소스의 ETag가 요청의 값과 일치하는지 확인합니다.

- 일치한다면 해당 조건을 만족하므로 저장을 진행할 수 있습니다.
- 일치하지 않는다면 다른 변경이 있었을 가능성이 있으므로 저장을 거부합니다.

조건이 실패했을 때 일반적으로 `412 Precondition Failed`를 반환합니다.

```http
HTTP/1.1 412 Precondition Failed
Content-Type: application/json

{
  "message": "문서가 수정되었습니다. 최신 내용을 확인해 주세요."
}
```

`If-Match`는 **강한 비교(strong comparison)**를 사용합니다. `W/"..."`처럼 약한 ETag는 이 비교에 일치하지 않으므로 수정 충돌 방지에 사용할 값은 적절한 강한 ETag여야 합니다. [MDN: If-Match](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/If-Match)

여기서 중요한 점은 헤더를 붙이는 것만으로 안전해지는 것이 아니라는 것입니다. **서버가 이 조건을 검증하고, 검증과 갱신을 안전하게 연결해야** 합니다.

## 4. 백엔드에서 확인과 저장을 하나의 연산으로 만들기

다음과 같은 흐름은 직관적이지만 위험할 수 있습니다.

```text
1. DB에서 버전 읽기
2. 요청 버전과 비교
3. 일치하면 DB 업데이트
```

2번과 3번 사이에 다른 요청이 데이터를 수정할 수 있기 때문입니다. 확인과 저장이 별개라면 그 사이에 다시 경쟁 상태가 생깁니다.

관계형 데이터베이스에서는 버전 조건을 업데이트 문에 포함할 수 있습니다.

```sql
UPDATE articles
SET
  title = $1,
  content = $2,
  version = version + 1
WHERE id = $3
  AND version = $4
RETURNING id, title, content, version;
```

`$4`는 사용자가 처음 읽은 버전입니다.

- 한 행이 반환되면 해당 버전을 기준으로 수정에 성공한 것입니다.
- 반환된 행이 없으면 버전이 달라졌거나 대상 행이 없는 상황입니다.

이때 **행이 없다는 이유만으로 무조건 버전 충돌이라고 단정해서는 안 됩니다.** 실제로 삭제되었거나 존재하지 않는 리소스일 수도 있습니다. API의 권한 정책과 응답 설계에 맞춰 구분하거나 적절한 오류를 반환해야 합니다.

변경 후 새 버전을 응답의 ETag로 전달하면 클라이언트는 다음 편집에 새 값을 사용할 수 있습니다.

```http
HTTP/1.1 200 OK
ETag: "article-42-v8"
Content-Type: application/json
```

버전 필드는 해당 리소스의 모든 관련 변경에서 일관되게 갱신되어야 합니다. 관리 화면에서는 버전을 올리지만 배치 작업에서는 올리지 않는다면, 충돌을 제대로 감지하지 못할 수 있습니다.

## 5. 프론트엔드의 역할: 충돌을 사용자 경험으로 연결하기

충돌을 감지하는 것만큼 중요한 것은 사용자가 작성한 내용을 잃지 않게 하는 것입니다.

```js
async function saveArticle(id, article, etag) {
  const response = await fetch(`/api/articles/${id}`, {
    method: "PUT",
    headers: {
      "Content-Type": "application/json",
      "If-Match": etag,
    },
    body: JSON.stringify(article),
  });

  if (response.status === 412) {
    return { status: "conflict" };
  }

  if (!response.ok) {
    throw new Error(`저장 실패: ${response.status}`);
  }

  return {
    status: "saved",
    article: await response.json(),
    etag: response.headers.get("ETag"),
  };
}
```

충돌이 발생했을 때 화면에서 할 일은 다음과 같습니다.

1. 사용자가 입력한 내용을 즉시 지우지 않습니다.
2. 다른 사용자의 변경으로 저장되지 않았음을 알려 줍니다.
3. 서버의 최신 내용을 다시 불러올 수 있게 합니다.
4. 가능하다면 내 변경과 최신 내용을 비교해 사용자가 병합하도록 돕습니다.
5. 사용자가 확인한 최신 버전을 기준으로 다시 저장합니다.

이때 프론트엔드가 `412`를 받자마자 새 ETag만 가져와 동일한 내용을 자동 재전송하면 안 됩니다. 그렇게 하면 충돌을 감지한 뒤에도 결국 다른 사람의 변경을 덮어쓸 수 있습니다.

## 6. `If-None-Match`는 어떤 역할일까?

비슷한 이름의 `If-None-Match`도 조건부 요청에 사용되지만, 목적을 구분해야 합니다.

대표적인 예는 캐시 재검증입니다.

```http
GET /api/articles/42 HTTP/1.1
If-None-Match: "article-42-v8"
```

서버의 표현이 해당 ETag와 일치한다면 서버는 본문 없이 `304 Not Modified`를 반환할 수 있고, 클라이언트는 보관 중인 응답을 재사용할 수 있습니다.

```http
HTTP/1.1 304 Not Modified
ETag: "article-42-v8"
```

정리하면 다음과 같습니다.

| 헤더 | 대표적인 사용 목적 |
|---|---|
| `If-Match` | 내가 읽은 버전이 현재 버전과 같을 때만 수정 |
| `If-None-Match` | 보관한 버전과 현재 버전이 같은지 확인해 캐시 재검증 |

`If-None-Match: *`는 지원하는 서버에서 해당 리소스가 아직 존재하지 않을 때만 생성하도록 조건을 거는 용도로도 사용할 수 있습니다. 다만 실제 사용 전에는 API가 조건부 요청을 올바르게 구현했는지 확인해야 합니다. [MDN: HTTP 조건부 요청](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Conditional_requests)

## 7. API 설계에서 놓치기 쉬운 부분

### 모든 변경이 같은 버전 체계를 따르는가?

관리자 API, 사용자 API, 백그라운드 작업이 모두 같은 데이터를 바꿀 수 있다면 어느 경로에서 수정하든 버전이 변경되어야 합니다. 한 경로라도 빠지면 오래된 데이터를 최신 데이터로 오인할 수 있습니다.

### 버전 비교와 저장이 원자적인가?

애플리케이션 코드에서 먼저 비교하고 나중에 저장하면 그 사이에 다른 요청이 끼어들 수 있습니다. 조건부 `UPDATE`처럼 데이터베이스에서 하나의 원자적 연산으로 처리하거나, 적절한 트랜잭션과 잠금 전략을 사용해야 합니다.

### ETag가 실제 응답 표현과 일치하는가?

사용자 권한이나 언어에 따라 같은 URL의 응답 내용이 달라질 수 있습니다. ETag를 설계할 때는 어떤 표현에 대한 검증자인지 명확해야 합니다. 단순한 DB 버전 번호가 모든 응답 변형에 그대로 적합한지는 API 설계에 따라 검토해야 합니다.

### `412`와 `409`를 구분하는가?

`If-Match` 같은 HTTP 사전 조건이 실패한 경우에는 `412`가 적합합니다. 반면 HTTP 사전 조건과 별개인 도메인 충돌은 API 설계에 따라 `409 Conflict` 등으로 표현할 수 있습니다. 두 상태를 기계적으로 혼용하기보다 클라이언트가 어떤 상황을 복구해야 하는지 일관되게 정의하는 것이 중요합니다.

## 8. 직접 확인해 볼 테스트

문서 수정 API에 다음 시나리오를 테스트로 추가해 보세요.

1. 같은 문서를 두 번 읽어 동일한 ETag를 얻습니다.
2. 첫 번째 요청이 해당 ETag로 문서를 수정합니다.
3. 두 번째 요청이 **이전 ETag**로 수정합니다.
4. 두 번째 요청이 `412`를 받는지 확인합니다.
5. DB에는 첫 번째 요청의 변경이 유지되는지 확인합니다.
6. 문서를 다시 읽어 새 ETag를 얻은 뒤 수정하면 성공하는지 확인합니다.

추가로 동시에 도착한 수정 요청을 테스트하면, 버전 확인과 업데이트 사이의 경쟁 상태를 발견하는 데 도움이 됩니다. 권한이 없는 사용자의 요청이나 문서가 삭제된 경우도 별도로 확인해야 합니다.

## 정리

낙관적 동시성 제어의 핵심 질문은 간단합니다.

> “내가 수정한 데이터가 여전히 서버의 최신 버전을 기준으로 하고 있는가?”

`ETag`와 `If-Match`는 이 질문을 HTTP 수준에서 표현하는 도구입니다. 백엔드는 버전 비교와 저장을 안전하게 수행하고, 프론트엔드는 충돌을 감지했을 때 사용자의 입력을 보존하며 복구를 도와야 합니다.

조건부 요청의 의미와 갱신 손실 방지에 관한 표준 설명은 [HTTP Semantics, RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)에서도 확인할 수 있습니다.

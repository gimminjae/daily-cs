# 좋은 API 설계

API는 프론트엔드와 백엔드 사이의 계약입니다. 데이터베이스 저장 구조를 그대로 노출하는 통로가 아니라, 화면과 권한에 맞춰 안정적으로 진화해야 하는 제품 인터페이스입니다.

## 리소스와 HTTP 메서드

리소스 중심 URL은 의도를 읽기 쉽게 합니다.

```http
GET    /members
GET    /members/member_123
POST   /members
PATCH  /members/member_123
DELETE /members/member_123
```

주문 취소, 이메일 재전송처럼 특별한 도메인 작업은 명시적 행동 URL을 사용할 수 있습니다.

```http
POST /orders/order_123/cancel
POST /emails/email_123/resend
```

GET은 조회를 뜻하며 서버 상태를 바꾸지 않아야 합니다. PATCH는 일부 필드 수정에 적합합니다.

## 일관된 데이터 계약

API는 데이터베이스 행 전체를 반환하면 안 됩니다. 비밀번호 해시, 내부 메모, 운영 상태처럼 외부에 노출하면 안 되는 값이 있을 수 있기 때문입니다. 화면과 권한에 맞는 DTO를 별도로 만듭니다.

필드 이름, 날짜 형식, null의 의미, 열거형 값, 금액 표현 규칙도 통일해야 합니다. 예를 들어 API는 camelCase를 쓰고 내부 DB는 snake_case를 쓰되 경계에서 변환할 수 있습니다.

목록 API에는 페이지네이션·필터·정렬 규칙이 필요합니다.

```http
GET /members?page=1&pageSize=20&sort=createdAt:desc
```

또는 데이터가 자주 변하는 피드에는 커서 기반 페이지네이션을 사용할 수 있습니다.

## 오류와 저장 응답

오류는 일관된 구조를 갖는 편이 좋습니다.

```json
{
  "code": "VALIDATION_ERROR",
  "message": "입력값을 확인해 주세요.",
  "fields": { "email": "올바른 이메일 형식이 아닙니다." },
  "requestId": "req_abc123"
}
```

HTTP 상태 코드와 안정적인 오류 코드를 함께 제공하면 프론트엔드는 입력 오류, 인증 만료, 권한 오류, 중복 충돌, 재시도 가능한 오류를 구분할 수 있습니다.

저장 API는 단순 success 값보다 서버가 확정한 최종 리소스를 반환하는 편이 좋습니다. 프론트엔드는 이를 바로 화면과 캐시에 반영할 수 있습니다.

## 멱등성과 버전 관리

주문·결제·초대처럼 중복 실행이 위험한 POST 요청에는 멱등성 키를 둡니다. 기존 클라이언트를 깨는 필드 삭제, 이름 변경, 타입 변경은 버전 또는 점진적 전환 전략을 검토해야 합니다. 새 선택적 필드 추가는 대체로 안전하지만, 클라이언트는 알 수 없는 열거형 값도 안전하게 처리해야 합니다.

문서는 구현과 함께 유지되는 계약서입니다. 엔드포인트, 인증, 요청·응답 예시, 오류, 권한, 페이지네이션, 변경 이력을 문서화해야 합니다.

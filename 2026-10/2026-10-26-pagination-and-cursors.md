# API 페이지네이션과 커서 기반 목록 조회

예상 읽기 시간: 약 10~15분

목록 API는 처음에는 단순해 보입니다. 게시글을 모두 반환하면 되기 때문입니다. 하지만 데이터가 수십만 건이 되면 응답 크기, DB 부하, 네트워크 비용, 화면 렌더링 시간이 함께 커집니다. 그래서 목록 API는 “어떤 데이터를 몇 개씩, 어떤 순서로, 다음 페이지를 어떻게 이어서 줄 것인가”를 명확히 설계해야 합니다.

## 1. 오프셋 방식

가장 익숙한 방식은 페이지 번호 또는 offset입니다.

~~~
GET /api/posts?page=3&limit=20
GET /api/posts?offset=40&limit=20
~~~

SQL은 보통 다음과 비슷합니다.

~~~
SELECT * FROM posts
ORDER BY created_at DESC
LIMIT 20 OFFSET 40;
~~~

장점은 사람이 이해하기 쉽고 “3페이지로 이동” 같은 UI에 잘 맞는다는 점입니다. 하지만 앞쪽 행을 건너뛰어야 하므로 뒤 페이지로 갈수록 비용이 커질 수 있습니다. 더 중요한 문제는 목록이 변하는 동안 페이지가 흔들린다는 것입니다.

사용자가 1페이지를 본 뒤 새 글이 여러 개 추가되면, 2페이지 요청에서 1페이지에 있던 항목이 다시 나타나거나 일부 항목이 건너뛸 수 있습니다.

## 2. 커서 기반 방식

커서 방식은 “몇 번째 페이지인가” 대신 “마지막으로 본 항목 뒤에서 시작하라”를 표현합니다.

~~~
GET /api/posts?limit=20&cursor=...
~~~

응답은 다음처럼 구성할 수 있습니다.

~~~
{
  "items": [ ... ],
  "nextCursor": "eyJjcmVhdGVkQXQiOiIyMDI2LTEwLTI2VDA5OjAwOjAwWiIsImlkIjoxMjN9",
  "hasMore": true
}
~~~

커서는 보통 정렬 기준과 고유 식별자를 함께 담습니다. 예를 들어 created_at만으로 정렬하면 같은 시각에 생성된 행의 순서가 모호할 수 있으므로 id를 보조 정렬 키로 둡니다.

~~~
SELECT *
FROM posts
WHERE (created_at, id) < ($cursorCreatedAt, $cursorId)
ORDER BY created_at DESC, id DESC
LIMIT 21;
~~~

21개를 가져와 20개만 반환하고 한 개가 더 있으면 hasMore를 true로 판단하는 방식이 흔합니다. 전체 개수를 매번 세지 않아도 다음 페이지 존재 여부를 알 수 있습니다.

## 3. 안정적인 정렬이 핵심이다

커서는 정렬 규칙과 분리될 수 없습니다. created_at 내림차순, id 내림차순으로 응답했다면 커서 조건도 정확히 같은 순서를 따라야 합니다.

정렬 기준이 자주 바뀌는 화면이라면 cursor에 정렬 종류를 포함하거나, 서버가 요청의 sort 값과 커서의 sort 값을 검증해야 합니다. 다른 정렬에서 발급된 커서를 그대로 쓰면 중복이나 누락이 생길 수 있습니다.

삭제된 항목도 고려해야 합니다. 마지막 항목이 삭제되어도 커서가 나타내는 위치 뒤의 데이터를 계속 조회할 수 있도록 설계하는 편이 일반적입니다.

## 4. 프론트엔드의 역할

무한 스크롤은 편리하지만 다음을 지켜야 합니다.

- 다음 페이지 요청이 진행 중일 때 중복 요청하지 않습니다.
- 같은 커서를 여러 번 요청해도 화면에 중복으로 합치지 않습니다.
- 필터나 정렬 조건이 바뀌면 목록과 커서를 함께 초기화합니다.
- 네트워크 오류 시 재시도 버튼과 현재까지 읽은 목록을 보존합니다.
- 접근성을 위해 “더 보기” 버튼도 제공하는 것을 고려합니다.

IntersectionObserver로 화면 하단을 감지해 다음 페이지를 가져올 수 있지만, 관찰 이벤트가 여러 번 발생할 수 있습니다. loading 상태와 요청 식별자를 두어 중복 호출을 막아야 합니다.

## 5. 전체 개수는 항상 필요하지 않다

“총 12,438개 중 1~20개”는 친절하지만, 큰 테이블에서 정확한 count가 비쌀 수 있습니다. 무한 스크롤에는 hasMore만으로 충분한 경우가 많습니다.

정확한 총수가 제품 요구사항이라면 별도 집계, 지연 계산, 근사치 표시를 검토할 수 있습니다. 단지 페이지 UI를 위해 매 요청마다 무거운 COUNT를 실행하는 것은 피해야 합니다.

## 마무리

오프셋은 임의 페이지 이동이 필요한 관리 화면에 편리합니다. 커서는 시간순 피드처럼 계속 변하고 뒤로 이어 읽는 목록에 더 안정적입니다.

핵심은 세 가지입니다. 정렬은 항상 결정적이어야 하고, 커서는 정렬 규칙과 함께 검증되어야 하며, 프론트엔드는 중복 요청·필터 변경·오류 복구를 명시적으로 다뤄야 합니다.

# 접근성은 프론트엔드만의 일이 아니다

접근성은 장애가 있는 사용자만을 위한 별도 기능이 아닙니다. 키보드로 조작하는 사람, 화면 확대가 필요한 사람, 소음 때문에 영상을 듣기 어려운 사람, 느린 네트워크에서 서비스를 이용하는 사람 모두에게 영향을 주는 제품 품질입니다.

프론트엔드에서는 의미 있는 구조와 키보드 조작, 오류 안내가 중요합니다. 백엔드에서도 읽기 쉬운 오류 응답, 적절한 데이터 구조, 접근 가능한 콘텐츠를 보존하는 API가 필요합니다. 화면만 고쳐서는 해결되지 않는 이유입니다.

## 1. 접근성은 네 가지 질문에서 시작한다

접근성 기준을 처음 접할 때는 다음 질문으로 접근할 수 있습니다.

- 인식: 사용자가 콘텐츠를 보고 듣거나 다른 방식으로 이해할 수 있는가?
- 운용: 마우스 없이 키보드나 보조 기술로 조작할 수 있는가?
- 이해: 입력 방법과 오류를 이해할 수 있는가?
- 견고성: 브라우저와 보조 기술이 의미와 상태를 해석할 수 있는가?

예를 들어 빨간 테두리만으로 입력 오류를 표시하면 색을 구분하기 어려운 사용자는 오류를 놓칠 수 있습니다. 아이콘만 있는 버튼에 이름이 없으면 화면 낭독기는 버튼의 목적을 전달하기 어렵습니다. 로딩 중 키보드 초점이 사라지면 사용자는 현재 위치를 알기 어렵습니다.

## 2. 의미 있는 HTML을 먼저 사용한다

웹에서 가장 좋은 기본 도구는 의미 있는 HTML입니다.

- 클릭하는 동작에는 button
- 다른 주소로 이동하는 동작에는 a
- 입력값에는 label과 input
- 페이지 구조에는 heading, main, nav
- 목록에는 ul 또는 ol
- 실제 표 데이터에는 table과 제목 셀

예를 들어 div에 클릭 이벤트만 붙이면 마우스로는 동작해도 키보드 포커스나 기본 키 조작이 빠질 수 있습니다. button을 사용하면 브라우저가 제공하는 기본 동작과 의미를 활용할 수 있습니다.

단, 기본 요소를 썼다고 모든 문제가 해결되는 것은 아닙니다. 버튼 이름이 모호하거나 초점 표시를 없애거나 비활성화 이유를 설명하지 않으면 여전히 사용하기 어렵습니다.

## 3. 키보드만으로 핵심 기능을 완료해 본다

마우스를 사용하지 않고 Tab, Shift+Tab, Enter, Space, 방향키, Escape로 서비스를 이용해 보세요. 다음을 확인합니다.

1. 모든 대화형 요소에 접근할 수 있는가?
2. 초점 순서가 화면의 의미 있는 흐름과 일치하는가?
3. 현재 초점이 보이는가?
4. 드롭다운과 모달을 열고 닫을 수 있는가?
5. 모달을 닫으면 원래 위치로 초점이 돌아가는가?
6. 키보드 초점이 어떤 영역에 갇히지 않는가?

모달이 열릴 때는 초점을 모달 안의 적절한 위치로 옮기고, 모달이 열린 동안 배경이 조작되지 않도록 처리해야 합니다. 닫을 때는 모달을 열었던 요소로 초점을 돌려주는 편이 좋습니다. 대화상자의 크기와 상황에 따라 초기 초점 위치는 신중하게 선택해야 합니다.

## 4. 화면 낭독기가 이해할 이름과 상태를 제공한다

화면 낭독기는 화면의 픽셀을 읽는 것이 아니라 접근성 트리에 담긴 역할, 이름, 상태를 전달합니다.

아이콘만 있는 삭제 버튼에 단순히 휴지통 그림만 있으면 사용자는 무엇을 삭제하는지 알기 어렵습니다. “삭제”보다 “김민재 회원 삭제”처럼 대상까지 포함한 이름이 도움이 될 수 있습니다.

상태도 전달해야 합니다.

- 메뉴가 열렸는지
- 체크박스가 선택됐는지
- 저장이 진행 중인지
- 검색 결과가 몇 개 나왔는지
- 오류가 발생했는지

ARIA는 HTML의 의미가 부족할 때 역할과 상태를 보완하는 도구입니다. 하지만 기본 HTML 요소로 해결할 수 있다면 그것을 우선하고, ARIA를 추가한 뒤 실제 키보드 동작과 상태가 맞는지 검증해야 합니다. 속성만 추가한다고 기능이 자동으로 구현되지는 않습니다.

## 5. 폼은 입력 전·입력 중·입력 후를 모두 설계한다

접근하기 쉬운 폼은 필드 이름과 입력 방법이 분명합니다. 플레이스홀더는 입력하면 사라지므로 라벨을 대체하지 않는 편이 좋습니다. 필수 여부와 입력 형식, 예를 들어 날짜 형식이나 비밀번호 조건도 입력 전에 알 수 있어야 합니다.

오류가 났을 때는 다음이 필요합니다.

- 어떤 필드에 문제가 있는지 표시
- 무엇이 잘못됐는지 구체적인 문장 제공
- 해결 방법 안내
- 색상만이 아닌 텍스트 또는 아이콘 사용
- 오류 메시지와 입력 필드의 연결
- 제출 실패 후 오류 요약 또는 첫 오류로 초점 이동 고려

“입력이 잘못되었습니다”보다는 “생년월일은 2026-10-20 형식으로 입력해 주세요”가 훨씬 유용합니다.

## 6. API 오류 구조가 접근성에 영향을 준다

백엔드가 모든 검증 오류를 하나의 문자열로 반환하면 프론트엔드는 어떤 필드에 오류를 연결해야 할지 알기 어렵습니다. 필드별 오류 코드와 메시지를 일관되게 제공하면 화면에서 각 입력값과 설명을 연결하기 쉽습니다.

```json
{
  "code": "VALIDATION_ERROR",
  "message": "입력값을 확인해 주세요.",
  "fields": {
    "email": "올바른 이메일 주소를 입력해 주세요.",
    "birthDate": "미래 날짜는 선택할 수 없습니다."
  },
  "requestId": "req_123"
}
```

프론트엔드는 각 필드에 해당 메시지를 표시하고, 화면 낭독기가 입력 요소의 설명을 함께 읽도록 연결할 수 있습니다. 동시에 서버는 유효성 검사의 최종 기준을 유지해야 합니다. 클라이언트 검증은 빠른 안내를 주지만, 서버 검증을 대신하지 않습니다.

오류 메시지에는 보안상 민감한 정보가 포함되지 않도록 주의해야 합니다. 내부 스택 추적이나 비밀 정보는 사용자 화면이 아니라 안전한 서버 로그에서 다뤄야 합니다.

## 7. 로딩과 비동기 결과도 전달해야 한다

시각적으로 스피너가 돌고 있어도 화면 낭독기 사용자에게는 아무 변화가 없을 수 있습니다. 저장 중, 저장 완료, 검색 결과 변경, 실패 상태를 적절한 텍스트로 제공해야 합니다.

다만 모든 작은 변화를 즉시 읽게 만들면 오히려 사용자의 흐름을 방해합니다. 중요한 상태 변화를 적절한 시점에 알리고, 긴급하지 않은 알림은 사용자의 현재 작업을 끊지 않도록 설계합니다.

예를 들어 검색 결과가 변경될 때 “검색 결과 12개”를 알리는 것은 도움이 됩니다. 키를 누를 때마다 모든 목록 내용을 반복해서 읽는 것은 방해가 될 수 있습니다.

## 8. 색상, 대비, 확대를 함께 고려한다

색상은 정보를 보조해야지 유일한 전달 수단이 되어서는 안 됩니다. 성공을 초록색, 오류를 빨간색으로 표시하더라도 “완료”, “오류”라는 텍스트와 적절한 아이콘을 함께 제공해야 합니다.

텍스트와 배경, 버튼 경계, 초점 표시의 대비도 확인해야 합니다. 작은 회색 텍스트는 디자인 시안에서는 세련돼 보여도 실제 모바일 환경이나 밝은 햇빛 아래에서는 읽기 어려울 수 있습니다.

화면을 확대하거나 글자 크기를 키워도 내용이 잘리지 않고, 버튼을 누를 수 있으며, 가로 스크롤이 과도하게 필요하지 않은지 확인합니다. 모바일에서는 터치 영역과 요소 간격도 중요합니다.

## 9. 이미지와 첨부 파일의 접근성

이미지에 대체 텍스트를 넣을 때는 이미지 파일명이 아니라 그 맥락에서 필요한 정보를 설명해야 합니다.

- 장식용 이미지는 보조 기술이 불필요하게 읽지 않도록 처리한다.
- 의미를 전달하는 이미지는 핵심 정보를 간결히 설명한다.
- 이미지 안의 글자가 중요하다면 같은 정보를 텍스트로도 제공한다.
- 차트는 제목, 단위, 주요 추세와 데이터 표를 함께 제공한다.

첨부 파일도 접근성 범위에 포함됩니다. PDF에 글자가 이미지로만 들어 있으면 검색과 화면 낭독이 어려울 수 있습니다. 백엔드는 대체 텍스트, 자막, 파일 유형과 같은 메타데이터를 저장하고 API로 전달할 수 있도록 지원해야 합니다.

## 10. 접근성 검증은 자동 검사와 실제 사용을 함께 한다

자동 검사 도구는 누락된 라벨, 일부 대비 문제, 잘못된 속성 등을 빠르게 발견합니다. 하지만 버튼 이름이 맥락상 적절한지, 초점 이동이 자연스러운지, 오류 문구가 이해하기 쉬운지는 사람의 판단이 필요합니다.

기본 검증 루틴을 정해 보세요.

1. 키보드만으로 회원가입, 로그인, 검색, 저장 흐름을 실행한다.
2. 화면 낭독기로 주요 화면의 이름·역할·상태를 확인한다.
3. 글자 크기와 화면 확대를 적용한다.
4. 모바일의 작은 화면과 큰 글자 설정을 확인한다.
5. 색상에 의존하지 않고 상태를 구분할 수 있는지 본다.
6. API 오류와 로딩·실패 상태가 실제로 전달되는지 검증한다.
7. 자동 검사 결과를 확인하되 수동 검증을 생략하지 않는다.

가능하다면 보조 기술을 사용하는 실제 사용자와 함께 테스트하는 것이 가장 많은 것을 알려 줍니다. 개발자가 예상하지 못한 탐색 방식과 불편을 발견할 수 있기 때문입니다.

## 오늘의 점검 질문

- [ ] 키보드만으로 주요 기능을 끝까지 사용할 수 있는가?
- [ ] 버튼과 입력 필드에 목적을 알 수 있는 이름이 있는가?
- [ ] 초점 위치가 보이고 모달을 닫은 뒤 원래 위치로 돌아가는가?
- [ ] 오류가 색상뿐 아니라 텍스트로도 설명되는가?
- [ ] API가 필드별 오류를 일관되게 제공하는가?
- [ ] 비동기 작업의 진행·완료·실패가 전달되는가?
- [ ] 이미지, 영상, 첨부 파일에 필요한 대체 정보가 있는가?
- [ ] 자동 검사와 키보드·화면 낭독기 수동 검증을 함께 하는가?

접근성은 마지막에 체크리스트를 통과시키는 작업이 아닙니다. 의미 있는 데이터와 인터페이스를 만들고, 다양한 사용자가 자신의 방식으로 작업을 완료할 수 있도록 처음부터 설계하는 일입니다.

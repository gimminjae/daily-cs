# 성능 최적화: 측정하고 병목을 분리하는 법

“느리다”는 하나의 문제가 아닙니다. 화면 렌더링, 네트워크, API 로직, 데이터베이스 쿼리, 이미지 크기, 캐시, 외부 서비스 중 어디에서 시간이 쓰이는지 먼저 분리해야 합니다.

## 사용자 경험으로 측정한다

서버 응답 시간만이 아니라 사용자가 중요한 화면을 언제 보는지, 클릭에 즉시 반응하는지, 로딩 이유를 알 수 있는지, 실패 뒤 재시도할 수 있는지를 봐야 합니다.

핵심 흐름 몇 개를 정해 측정합니다.

- 앱 실행에서 홈 화면 표시
- 로그인에서 프로필 조회
- 회원 목록 조회와 검색
- 정보 수정에서 저장 완료
- 게시글 작성에서 목록 반영

평균값만 보지 말고 p95·p99도 봐야 합니다. 평균이 빠르더라도 일부 사용자가 수 초를 기다릴 수 있습니다.

## 프론트엔드 병목

상태 변경마다 넓은 컴포넌트가 다시 렌더링되거나, 긴 목록을 모두 그리거나, 큰 원본 이미지를 표시하면 화면이 느려집니다. 목록이 클 때는 페이지네이션, 무한 스크롤, 가상 목록을 검토합니다.

검색어 입력마다 API 요청을 보내는 기능에는 디바운스를 적용할 수 있습니다. 다만 모든 입력에 적용하는 것이 아니라, 서버 검색처럼 요청이 잦은 기능에 선택적으로 사용합니다.

## API와 데이터베이스 병목

목록 하나를 조회한 뒤 각 행마다 추가 쿼리를 실행하는 N+1 문제는 흔한 병목입니다. 조인, 배치 조회, 필요한 필드만 선택하는 방식으로 쿼리 수를 줄입니다.

인덱스는 자주 필터·정렬·조인하는 데이터를 빠르게 찾게 하지만, 모든 열에 추가하면 쓰기 비용과 저장 공간이 증가합니다. 느린 쿼리 로그와 실행 계획을 보고 실제로 필요한 인덱스를 결정해야 합니다.

목록 API는 필요한 범위만 반환해야 합니다. 기본 페이지 크기, 최대 크기, 정렬 기준, 다음 페이지 여부를 API 계약으로 명확히 둡니다.

## 캐시와 비동기 작업

캐시는 빠른 읽기를 제공하지만 오래된 데이터를 보여 줄 수 있습니다. 프로필 수정 뒤 어느 캐시를 즉시 갱신하고 어느 목록을 무효화할지 정해야 합니다. 권한·재고·결제 상태는 오래된 캐시가 특히 위험합니다.

저장 뒤 이메일 발송, 통계 집계, 검색 인덱스 갱신처럼 사용자가 즉시 기다릴 필요 없는 일은 비동기 작업으로 넘길 수 있습니다. 다만 재시도·중복 실행·실패 알림 정책을 함께 설계해야 합니다.

성능 개선은 측정 → 병목 분리 → 작은 개선 → 재측정 → 회귀 확인의 반복입니다.

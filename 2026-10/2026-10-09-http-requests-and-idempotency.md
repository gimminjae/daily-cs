# HTTP 요청과 멱등성

사용자가 버튼을 한 번 눌렀다고 해서 서버가 요청을 한 번만 받는 것은 아닙니다. 네트워크 지연, 응답 유실, 앱의 자동 재시도, 연속 클릭 때문에 동일한 요청이 여러 번 서버에 도착할 수 있습니다. 결제·주문·초대처럼 중복 실행이 위험한 기능에서는 이를 전제로 설계해야 합니다.

## 타임아웃은 실패를 뜻하지 않는다

클라이언트가 10초 안에 응답을 받지 못했더라도 서버가 11초째에 작업을 완료했을 수 있습니다. 따라서 타임아웃 직후 무조건 새 요청을 보내면 결제나 주문이 중복될 수 있습니다. 안전한 흐름은 다음과 같습니다.

1. 요청을 시작할 때 고유한 멱등성 키를 만든다.
2. 같은 사용자 행동에서 재시도할 때는 같은 키를 사용한다.
3. 서버는 키와 요청 내용을 함께 저장한다.
4. 같은 키의 요청이 다시 오면 새 작업을 만들지 않고 이전 결과를 돌려준다.
5. 응답이 불명확하면 같은 키로 재시도하거나 상태 조회 API를 사용한다.

```http
POST /payments
Idempotency-Key: 4d3f...

{ "orderId": "order_123", "amount": 25000 }
```

서버는 동일한 키에 서로 다른 주문이나 금액이 들어오는 경우 오류로 처리해야 합니다. 키만 같다고 이전 결과를 돌려주면 요청을 잘못 재사용할 수 있기 때문입니다.

## 프론트엔드와 백엔드의 역할

프론트엔드는 로딩 중 버튼을 비활성화하고, 재시도 여부를 구분하며, “실패”와 “처리 결과를 알 수 없음”을 다른 상태로 보여 줍니다. 하지만 버튼 비활성화만으로 중복 요청을 막을 수는 없습니다. 여러 탭, 다른 기기, 네트워크 라이브러리의 재시도는 프론트엔드 제어 밖에서 발생합니다.

백엔드는 데이터베이스 제약 조건과 트랜잭션을 사용해 최후의 안전망을 둡니다. 주문 번호, 외부 결제 거래 ID, 멱등성 키처럼 중복되면 안 되는 값에는 유니크 제약 조건이 필요합니다. 애플리케이션 코드의 사전 확인만으로는 동시 요청을 완전히 막지 못합니다.

## 오류 설계와 추적

프론트엔드가 적절히 반응하려면 백엔드는 의미 있는 상태 코드와 안정적인 오류 코드를 제공해야 합니다.

- 400: 요청 형식 또는 값 오류
- 401: 인증 필요
- 403: 권한 없음
- 409: 중복 또는 상태 충돌
- 422: 비즈니스 규칙 위반
- 429: 요청 제한 초과
- 500: 서버 내부 오류

요청 ID를 프론트엔드·API 서버·외부 결제 서비스 로그에 연결하면 “결제가 이상합니다” 같은 문의를 추적하기 쉬워집니다. 단, 토큰과 개인정보는 로그에 남기지 않아야 합니다.

## 점검 질문

- 같은 요청이 두 번 오면 최종 결과가 안전한가?
- 타임아웃 뒤에 사용자가 무엇을 해야 하는가?
- 데이터베이스가 중복 생성을 막는가?
- 오류 코드가 다음 행동을 결정할 만큼 구체적인가?
- 운영 중 요청 흐름을 추적할 수 있는가?

안정적인 서비스는 네트워크 실패·중복 요청·동시성 같은 평범한 현실을 잘 다루는 데서 시작합니다.

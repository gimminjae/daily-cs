# 데이터베이스 인덱스와 쿼리 플랜

예상 읽기 시간: 약 10~15분

서비스가 느려졌을 때 “인덱스를 추가하자”는 말은 자주 나옵니다. 하지만 인덱스는 모든 쿼리를 빠르게 하는 마법이 아닙니다. 읽기를 빠르게 하는 대신 쓰기 비용과 저장 공간을 늘리고, 잘못된 인덱스는 거의 사용되지 않거나 오히려 운영 복잡도만 키웁니다.

## 1. 인덱스는 책의 색인과 비슷하다

테이블을 처음부터 끝까지 읽어 조건에 맞는 행을 찾는 작업을 전체 테이블 스캔이라고 생각할 수 있습니다. 행이 적으면 괜찮지만 수백만 행에서는 비용이 커집니다.

인덱스는 특정 열의 값과 행 위치를 정렬된 구조로 보관해, 필요한 범위를 더 적게 찾게 합니다.

~~~
SELECT id, title
FROM posts
WHERE author_id = 42
ORDER BY created_at DESC
LIMIT 20;
~~~

이 쿼리가 자주 실행된다면 author_id와 created_at을 함께 고려한 인덱스가 후보가 될 수 있습니다.

~~~
CREATE INDEX posts_author_created_at_idx
ON posts (author_id, created_at DESC);
~~~

인덱스 설계는 쿼리의 WHERE, JOIN, ORDER BY, LIMIT을 함께 봐야 합니다.

## 2. 복합 인덱스의 열 순서

복합 인덱스는 열 순서가 중요합니다. (author_id, created_at) 인덱스는 author_id로 먼저 좁힌 뒤 created_at 순서를 활용하는 쿼리에 적합합니다.

반대로 created_at만 기준으로 최근 글을 가져오는 쿼리에는 이 인덱스를 효율적으로 쓰지 못할 수 있습니다. 앞선 열 조건 없이 뒤 열만 사용하는 경우를 항상 빠르게 해 주지는 않기 때문입니다.

일반적인 출발점은 다음입니다.

1. 동등 비교 조건을 먼저 고려합니다.
2. 범위 조건과 정렬 조건을 뒤에서 검토합니다.
3. 실제 쿼리 플랜으로 추측을 검증합니다.

다만 이 규칙은 출발점일 뿐입니다. 데이터 분포, DB 종류, 통계 정보에 따라 최선의 선택은 달라집니다.

## 3. 읽기만 빨라지고 쓰기는 느려진다

새 인덱스는 INSERT, UPDATE, DELETE 때도 갱신돼야 합니다. 즉 인덱스가 많을수록 쓰기는 느려지고 저장 공간과 유지 관리 비용이 늘어납니다.

특히 자주 변하는 열에 여러 인덱스를 만들면 변경마다 많은 구조를 업데이트해야 합니다. “느린 쿼리 하나”를 해결하려고 무작정 인덱스를 쌓기보다, 해당 쿼리의 빈도와 영향도를 먼저 확인해야 합니다.

## 4. EXPLAIN으로 실제 실행을 확인한다

인덱스를 만들었다면 실제로 사용되는지 확인해야 합니다.

~~~
EXPLAIN ANALYZE
SELECT id, title
FROM posts
WHERE author_id = 42
ORDER BY created_at DESC
LIMIT 20;
~~~

DB마다 표현은 다르지만 보통 다음을 봅니다.

- 전체 스캔인지, 인덱스 스캔인지
- 예상 행 수와 실제 행 수가 크게 다른지
- 정렬 작업이 별도로 발생하는지
- 실행 시간이 어디에서 많이 쓰이는지
- 반환 행 수에 비해 읽은 행 수가 과도하지 않은지

개발 환경의 작은 데이터에서는 인덱스가 효과 있어 보여도, 운영 데이터의 분포에서는 다를 수 있습니다. 운영과 유사한 데이터 규모에서 측정하는 것이 중요합니다.

## 5. 선택도가 낮은 열의 함정

성별, 상태값처럼 가능한 값이 적은 열은 선택도가 낮습니다. 예를 들어 status가 active인 행이 전체의 95%라면 status 단일 인덱스는 많은 행을 다시 읽어야 해서 큰 이점이 없을 수 있습니다.

반대로 특정 상태이면서 최근 생성된 행만 조회하는 패턴이라면 복합 인덱스나 부분 인덱스를 검토할 수 있습니다.

~~~
CREATE INDEX posts_published_created_at_idx
ON posts (created_at DESC)
WHERE status = 'published';
~~~

부분 인덱스는 특정 조건을 만족하는 행만 담아 크기를 줄일 수 있지만, 해당 조건과 맞는 쿼리에서만 효과가 있습니다.

## 6. ORM이 만든 쿼리도 확인한다

ORM은 생산성을 높이지만, 생성되는 SQL의 비용까지 자동으로 최적화해 주지는 않습니다.

대표적인 문제는 N+1 쿼리입니다. 목록 20개를 조회한 후, 각 항목의 작성자를 다시 조회하면 총 21번의 쿼리가 발생할 수 있습니다. 해결 방법은 상황에 따라 JOIN, eager loading, 배치 조회, 응답 구조 변경 등이 될 수 있습니다.

인덱스는 N+1을 약간 빠르게 할 수는 있어도, 불필요하게 많은 왕복 자체를 없애지는 못합니다.

## 7. 인덱스를 추가하기 전 점검표

1. 실제로 느린 쿼리인가? 로그와 지표로 확인했는가?
2. WHERE, JOIN, ORDER BY, LIMIT 조건은 무엇인가?
3. 반환 행 수와 읽는 행 수는 얼마나 차이 나는가?
4. 기존 인덱스와 겹치지 않는가?
5. 쓰기 부하와 저장 공간 증가는 감당 가능한가?
6. EXPLAIN ANALYZE에서 개선을 확인했는가?
7. 대용량 테이블의 인덱스 생성이 운영 트래픽에 미칠 영향은 검토했는가?

## 마무리

인덱스는 데이터 접근 경로를 설계하는 도구입니다. 쿼리 모양과 데이터 분포를 이해하고, 실행 계획으로 검증할 때 가장 효과적입니다.

핵심은 세 가지입니다. 모든 열에 인덱스를 만들지 말고, 읽기 성능과 쓰기 비용을 함께 고려하며, 반드시 실제 실행 계획과 운영 지표로 효과를 검증하세요.

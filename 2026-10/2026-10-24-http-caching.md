# HTTP 캐싱: 빠른 서비스와 최신 데이터를 함께 설계하는 법

예상 읽기 시간: 약 10~15분

웹 성능의 캐시는 단순히 “응답을 저장해 다음 요청을 빠르게 처리하는 기능”이 아닙니다. 잘못된 캐시는 사용자가 이미 수정한 정보 대신 오래된 화면을 보게 하고, 더 심하면 다른 사용자의 데이터를 노출할 수 있습니다.

오늘은 HTTP 캐싱의 기본 모델과 Cache-Control, ETag, Vary를 중심으로 프론트엔드와 백엔드가 함께 결정해야 할 정책을 살펴보겠습니다.

## 1. 캐시는 어디에 있을까?

한 요청은 여러 캐시를 거칠 수 있습니다.

~~~
브라우저 메모리/디스크 → CDN·리버스 프록시 → 애플리케이션 → DB
~~~

- 브라우저 캐시는 보통 한 사용자의 브라우저에 저장됩니다.
- 공유 캐시는 CDN이나 리버스 프록시처럼 여러 사용자가 함께 재사용할 수 있습니다.
- 애플리케이션 캐시는 Redis 같은 별도 저장소에 비즈니스 데이터를 저장하는 경우입니다.

이 글은 주로 HTTP 응답 헤더를 이용하는 브라우저·공유 캐시를 다룹니다. HTTP 캐시는 같은 요청을 다시 처리할 필요를 줄여 응답 시간과 네트워크 사용량을 줄이는 것이 목적입니다. [RFC 9111: HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111.html)

모든 데이터를 같은 방식으로 캐시하면 안 됩니다. 공개 정적 파일, 공개 상품 정보, 로그인 사용자 프로필, 결제 결과는 각각 잘못된 값이 보여질 때의 위험도가 다릅니다. 따라서 캐시 시간도 달라야 합니다.

## 2. 신선함과 오래됨

캐싱에서 중요한 개념은 신선함입니다. 캐시는 응답을 저장한 뒤, 정책이 허용하는 시간 동안 원본 서버에 묻지 않고 그 응답을 재사용할 수 있습니다.

~~~
Cache-Control: max-age=60
~~~

이 응답은 생성 또는 검증된 뒤 60초 동안 신선한 것으로 취급될 수 있습니다. 신선한 응답을 재사용하면 서버 왕복이 없으므로 빠릅니다. 반대로 시간이 지나면 응답은 오래된 상태가 되고, 일반적으로 재검증하거나 새 응답을 받아야 합니다.

max-age=60은 정확히 60초 후 화면이 자동으로 바뀐다는 뜻이 아닙니다. HTTP 캐시가 응답을 재사용할 수 있는 기간을 설명할 뿐입니다. 화면의 상태 관리, 서비스 워커, 브라우저 뒤로가기 동작은 별도의 영향을 받을 수 있습니다.

과거에는 Expires도 많이 사용했지만, 상대 시간인 max-age가 서버와 클라이언트의 시계 차이에 덜 민감해 보통 더 다루기 편합니다. [MDN: Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)

## 3. no-store와 no-cache는 다르다

이름이 비슷해 자주 혼동하는 두 지시어가 있습니다.

### no-store

~~~
Cache-Control: no-store
~~~

응답을 저장하지 않도록 지시합니다. 민감한 개인정보나 일회성 인증 관련 응답처럼 보관 자체를 원하지 않는 경우에 검토합니다.

하지만 이것만으로 브라우저의 화면 기록, 서버 로그, 사용자가 내려받은 파일 등 모든 복사본이 사라지는 것은 아닙니다. HTTP 캐시에 대한 정책일 뿐이며, 민감한 데이터 보호에는 HTTPS, 인증·인가, 로그 정책도 필요합니다.

### no-cache

~~~
Cache-Control: no-cache
~~~

이름과 달리 “저장하지 말라”는 뜻이 아닙니다. 저장은 가능하지만, 재사용하기 전에 원본 서버에 재검증해야 한다는 의미입니다.

따라서 최신성이 중요하지만 본문을 매번 다시 전송할 필요는 없는 공개 문서에 유용할 수 있습니다. 변경되지 않았다면 서버가 본문 대신 304 Not Modified를 반환할 수 있기 때문입니다.

> no-store는 보관을 막고, no-cache는 재사용 전에 확인을 요구합니다.

## 4. 재검증: ETag와 304

재검증은 이미 저장한 응답이 여전히 같은지 확인하는 과정입니다. 서버는 응답에 특정 버전을 나타내는 ETag를 보낼 수 있습니다.

~~~
HTTP/1.1 200 OK
ETag: "post-42-v7"
Cache-Control: no-cache
Content-Type: application/json

{ "id": 42, "title": "캐시 이해하기" }
~~~

다음 요청에서 캐시는 저장한 ETag를 이용해 조건부 요청을 보낼 수 있습니다.

~~~
GET /api/posts/42 HTTP/1.1
If-None-Match: "post-42-v7"
~~~

내용이 변하지 않았다면 서버는 본문을 다시 보내지 않고 응답합니다.

~~~
HTTP/1.1 304 Not Modified
ETag: "post-42-v7"
~~~

이 방식은 최신성을 확인하면서도 본문 전송량을 줄입니다. ETag는 낙관적 동시성 제어의 If-Match에도 사용될 수 있지만, 여기서는 “저장한 응답이 아직 유효한가?”를 확인하는 용도입니다. [MDN: ETag](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/ETag)

재검증은 원본 서버와의 왕복을 완전히 없애지는 못합니다. 따라서 변경되지 않는 정적 파일은 긴 신선도 기간을 주는 편이 더 효율적일 수 있습니다.

## 5. 정적 파일에는 콘텐츠 해시를 사용한다

배포 시 파일 이름에 내용 해시를 넣으면, 파일 내용이 바뀔 때 URL도 바뀝니다.

~~~
/app.82a1c9.js
/app.f15d03.js
~~~

새 파일은 새 URL이므로 이전 파일을 길게 캐시해도 새 배포를 막지 않습니다.

~~~
Cache-Control: public, max-age=31536000, immutable
~~~

이 패턴은 번들된 JavaScript, CSS, 폰트, 이미지에 잘 맞습니다. 단, URL이 변하지 않는 app.js에 같은 정책을 적용하면 사용자가 오래된 파일을 계속 받을 수 있으므로 위험합니다.

immutable은 신선한 기간 동안 변하지 않을 것이라는 의도를 표현합니다. 이 약속은 서버가 지켜야 합니다. “캐시를 무효화하기 위해 같은 URL에 새 내용을 덮어쓰기”는 장기 캐시 전략과 충돌합니다.

## 6. 공유 캐시와 개인 데이터

공유 캐시는 여러 사용자에게 같은 응답을 재사용할 수 있습니다. 그래서 공개 콘텐츠에는 큰 효과가 있지만, 사용자별 응답에 잘못 적용하면 심각한 문제가 됩니다.

~~~
GET /api/me
Authorization: Bearer ...
~~~

이런 응답을 CDN이 다른 사용자에게 재사용하면 안 됩니다. 안전한 출발점은 개인 응답에 공유 캐시를 허용하지 않는 것입니다.

~~~
Cache-Control: private, no-store
~~~

모든 인증 요청이 무조건 캐시 불가인 것은 아니지만, 공유 캐시가 Authorization이 포함된 요청의 응답을 재사용하려면 명시적인 허용 정책과 정확한 키 설계가 필요합니다. 기본값을 “의심스러우면 공유 캐시하지 않는다”로 잡는 편이 안전합니다. [RFC 9111의 인증 요청 저장 규칙](https://www.rfc-editor.org/rfc/rfc9111.html)

응답에 Set-Cookie가 있다고 해서 캐싱이 자동으로 완전히 금지되는 것도 아닙니다. 민감한 응답은 의도한 Cache-Control을 명시해야 합니다.

## 7. Vary: 같은 URL의 서로 다른 표현을 구분하기

같은 URL이라도 요청 헤더에 따라 응답이 달라질 수 있습니다. 예를 들어 언어별 콘텐츠를 반환한다고 가정해 보겠습니다.

~~~
GET /api/articles/42
Accept-Language: ko
~~~

서버가 한국어 응답을 저장하게 한 뒤, 영어 사용자의 요청에도 같은 캐시 항목을 준다면 문제가 됩니다. 이때 서버는 다음처럼 응답을 구분해야 함을 알립니다.

~~~
Vary: Accept-Language
~~~

Vary는 캐시 키를 구성할 때 추가로 고려해야 할 요청 헤더를 지정합니다. CORS에서 요청의 Origin에 따라 다른 Access-Control-Allow-Origin을 반환하는 서버도 Vary: Origin을 고려해야 합니다.

무분별하게 Vary에 많은 헤더를 넣으면 캐시 재사용률이 낮아질 수 있습니다. 반대로 필요한 헤더를 빼면 잘못된 표현을 재사용할 수 있습니다. 응답 내용을 실제로 바꾸는 헤더만 신중하게 지정해야 합니다.

## 8. stale-while-revalidate와 장애 대응

신선도 기간이 끝난 응답을 곧바로 버리지 않고, 일시적으로 사용자에게 보여 주면서 뒤에서 재검증하는 전략도 있습니다.

~~~
Cache-Control: max-age=60, stale-while-revalidate=300
~~~

처음 60초는 신선한 응답을 사용합니다. 그 이후 일정 기간에는 이전 응답을 빠르게 제공하고, 백그라운드에서 새 버전을 확인할 수 있습니다. 다음 사용자 요청은 갱신된 응답을 받을 가능성이 있습니다. [MDN: stale-while-revalidate](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)

이는 뉴스 목록, 공개 카탈로그처럼 수 분의 지연이 허용되고 빠른 응답이 중요한 화면에 유용할 수 있습니다. 반면 재고, 권한, 결제 상태처럼 잘못된 값이 즉시 문제를 일으키는 화면에는 부적합할 수 있습니다.

stale-if-error는 원본 서버 오류 시 오래된 응답을 일정 기간 제공하도록 허용하는 지시어입니다. 장애 시 완전히 빈 화면을 보여 주는 것보다 나을 수 있지만, 오래된 정보라는 사실이 위험한 도메인에서는 주의해야 합니다.

## 9. 캐시 무효화는 설계의 일부다

데이터를 변경한 직후 사용자가 오래된 데이터를 보는 문제는 자주 발생합니다. 예를 들어 게시글 수정 API가 성공한 뒤 목록 페이지가 이전 응답을 보여 줄 수 있습니다.

해결 방법은 한 가지가 아닙니다.

- 정적 리소스는 새 URL, 즉 콘텐츠 해시를 만듭니다.
- 공개 데이터는 짧은 max-age와 재검증 정책을 둡니다.
- 애플리케이션의 데이터 캐시는 수정 성공 시 관련 키나 태그를 무효화합니다.
- 프론트엔드는 수정 성공 응답으로 로컬 상태를 갱신하고, 필요한 경우 최신 데이터를 다시 가져옵니다.

중요한 것은 “서버에서 업데이트했으니 모든 캐시가 즉시 사라질 것”이라고 가정하지 않는 것입니다. 브라우저, CDN, 프레임워크 데이터 캐시가 각각 다른 정책으로 동작할 수 있습니다.

## 10. 실무 점검표

새 엔드포인트를 만들 때 다음 질문을 확인해 보세요.

1. 이 응답은 사용자마다 다른가, 공개적으로 같은가?
2. 잘못된 정보가 몇 초·몇 분 보여도 괜찮은가?
3. 저장 자체를 피해야 하는 민감 정보가 있는가?
4. 변경되지 않는 파일의 URL은 콘텐츠 변경 시 달라지는가?
5. 응답이 언어, Origin, 기기 형식에 따라 달라진다면 Vary는 올바른가?
6. CDN과 브라우저에 각각 어떤 캐시 정책이 적용되는가?
7. 수정 요청 후 관련 화면과 캐시를 어떻게 갱신하는가?
8. 실제 운영 응답의 Cache-Control, Age, ETag, CDN 헤더를 확인했는가?

브라우저 개발자 도구 Network 탭에서 요청 헤더와 응답 헤더를 보며, 첫 요청과 새로고침 요청이 각각 캐시·재검증·원본 호출 중 어느 경로를 탔는지 확인하는 습관이 좋습니다.

## 마무리

좋은 캐싱은 단순히 긴 max-age를 붙이는 일이 아닙니다. 데이터의 공개 범위와 최신성 요구를 먼저 정하고, 정적 파일에는 버전이 바뀌는 URL을, 변경 가능한 공개 데이터에는 재검증 또는 적절한 stale 전략을, 민감한 개인 데이터에는 보수적인 저장 정책을 적용하는 일입니다.

핵심은 세 가지입니다. **캐시 수명은 데이터의 위험도에 맞춰 정하고, URL이 바뀌지 않는 리소스에는 무기한 캐시를 주지 않으며, 캐시는 배포와 데이터 변경 흐름까지 포함해 검증한다**는 것입니다.

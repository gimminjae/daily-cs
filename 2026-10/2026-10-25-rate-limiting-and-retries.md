# API 레이트 리밋과 재시도 설계

예상 읽기 시간: 약 10~15분

사용자가 버튼을 여러 번 눌렀거나, 버그 난 클라이언트가 짧은 시간에 수천 번 요청했거나, 외부 API가 갑자기 느려졌다고 가정해 보겠습니다. 서버는 요청 하나를 처리할 수 있어도 모든 요청을 동시에 처리할 수는 없습니다.

이때 필요한 것이 **레이트 리밋(rate limiting)**입니다. 레이트 리밋은 단순히 “요청을 막는 장치”가 아니라, 서비스의 공정성·가용성·비용을 관리하는 정책입니다. 동시에 클라이언트는 거부된 요청을 무작정 반복하지 않고, 안전한 방식으로 재시도해야 합니다.

## 1. 무엇을 제한할까?

제한 대상은 서비스 성격에 따라 달라집니다.

- IP 주소별 요청 수
- 로그인 사용자별 요청 수
- API 키 또는 애플리케이션별 요청 수
- 특정 엔드포인트별 요청 수
- 무거운 작업의 동시 실행 수
- 조직이나 요금제별 사용량

로그인 API는 IP와 계정 단위의 제한이 모두 필요할 수 있습니다. 이미지 변환 API는 요청 수보다 동시 작업 수나 처리 시간 제한이 더 중요할 수 있습니다.

IP만 기준으로 잡으면 회사·학교·모바일 통신망처럼 같은 IP를 공유하는 정상 사용자가 함께 제한될 수 있습니다. 반대로 인증된 사용자만 기준으로 잡으면 로그인 전 공격을 충분히 방어하지 못할 수 있습니다.

## 2. 대표적인 제한 알고리즘

### 고정 윈도우

“매 분마다 100회”처럼 고정된 시간 구간에 카운터를 둡니다. 구현은 쉽지만 경계 문제가 있습니다. 사용자가 12:00:59에 100번, 12:01:00에 다시 100번 요청하면 매우 짧은 시간에 200번을 보낼 수 있습니다.

### 슬라이딩 윈도우

최근 60초처럼 현재 시점 기준으로 이동하는 구간을 계산합니다. 고정 윈도우의 경계 급증을 완화하지만, 요청 기록을 더 정교하게 관리해야 할 수 있습니다.

### 토큰 버킷

버킷에 토큰이 일정 속도로 채워지고, 요청 하나가 토큰 하나를 소비합니다. 토큰이 남아 있으면 짧은 순간의 요청 급증은 허용하면서, 평균 요청률은 제한할 수 있습니다.

### 리키 버킷

들어온 요청을 일정한 속도로 흘려보냅니다. 처리량을 일정하게 만드는 데 유용하지만, 즉시 처리되어야 하는 요청에는 대기 시간이 생길 수 있습니다.

알고리즘보다 먼저 “누구의 어떤 자원을, 어느 시간 범위에서 보호할 것인가”를 정해야 합니다.

## 3. 서버 응답

한도를 넘은 요청에는 일반적으로 429 Too Many Requests를 반환할 수 있습니다.

~~~
HTTP/1.1 429 Too Many Requests
Retry-After: 60
Content-Type: application/json

{
  "code": "RATE_LIMITED",
  "message": "요청이 너무 많습니다. 잠시 후 다시 시도해 주세요."
}
~~~

Retry-After는 클라이언트가 다음 요청 전 기다려야 할 시간을 초 단위나 HTTP 날짜로 나타낼 수 있습니다. [MDN: 429](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/429), [MDN: Retry-After](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Retry-After)

응답 본문에는 사람이 읽을 메시지뿐 아니라, 클라이언트가 처리할 수 있는 안정적인 오류 코드도 두는 편이 좋습니다. UI는 재시도 시각을 보여 줄 수 있고, 배치 작업은 큐에 재등록할 수 있습니다.

하지만 공격 상황에서 모든 요청에 정교한 JSON 오류를 생성하는 것 자체가 부담이 될 수 있습니다. 상황에 따라 연결을 끊거나, 상위 CDN·WAF·API 게이트웨이에서 먼저 차단하는 전략도 필요합니다.

## 4. 재시도는 모든 오류에 하면 안 된다

클라이언트에서 실패했다고 무조건 재시도하면 장애를 키울 수 있습니다.

| 상황 | 일반적인 처리 |
|---|---|
| 네트워크 일시 오류 | 제한된 횟수로 재시도 검토 |
| 429 | Retry-After를 우선 존중 |
| 503 등 일시적 서버 오류 | 백오프와 함께 재시도 검토 |
| 400 유효성 오류 | 수정 없이는 재시도하지 않음 |
| 401·403 인증/권한 오류 | 인증 흐름 또는 사용자 안내 |
| 결제·주문 POST 타임아웃 | 상태 확인 후 멱등성 키로 처리 |

특히 쓰기 요청은 주의해야 합니다. 클라이언트가 타임아웃을 받았더라도 서버는 이미 주문을 생성했을 수 있습니다. 같은 요청을 다시 보내면 중복 주문이나 중복 결제가 생길 수 있습니다.

이 문제는 멱등성 키로 완화할 수 있습니다.

~~~
POST /api/orders
Idempotency-Key: 7c2b...
~~~

서버는 같은 키의 요청을 같은 작업으로 인식하고, 이미 처리한 결과를 반환하거나 진행 상태를 알려 줍니다. 재시도 정책은 서버의 멱등성 보장과 함께 설계해야 합니다.

## 5. 지수 백오프와 지터

재시도 간격을 매번 같게 하면 장애가 난 서버에 클라이언트가 한꺼번에 다시 몰릴 수 있습니다. 이를 피하기 위해 지수 백오프를 사용합니다.

~~~
1초 → 2초 → 4초 → 8초
~~~

여기에 지터(jitter), 즉 무작위 흔들림을 더합니다.

~~~
function backoffDelay(attempt) {
  const base = Math.min(1000 * 2 ** attempt, 30_000);
  return Math.random() * base;
}
~~~

많은 클라이언트가 같은 시각에 실패해도 재시도 시점을 분산할 수 있습니다. 다만 무한 재시도는 금물입니다. 최대 횟수, 전체 시간 제한, 사용자 취소, 요청의 중요도를 함께 정해야 합니다.

서버가 Retry-After를 보냈다면 임의 백오프보다 해당 값을 우선하는 것이 일반적으로 바람직합니다.

## 6. 프론트엔드 사용자 경험

레이트 리밋은 정상 사용자에게도 보일 수 있습니다. 따라서 단순한 오류보다 복구 가능한 안내가 필요합니다.

- 버튼을 누른 직후 중복 클릭을 막습니다.
- 저장 중 상태를 명확하게 표시합니다.
- 검색 자동완성에는 디바운스를 적용합니다.
- 429를 받으면 재시도 가능 시각을 안내합니다.
- 사용자가 취소할 수 있는 요청은 AbortController로 취소합니다.
- 실패한 쓰기 작업을 자동 재시도할 때는 멱등성 보장을 확인합니다.

검색창은 입력할 때마다 요청하기보다 200~300ms 정도 디바운스를 적용할 수 있습니다. 반면 결제처럼 즉시 반응해야 하는 작업은 디바운스보다 제출 중 상태와 중복 요청 방지가 더 적절합니다.

## 7. 백엔드 운영 점검

레이트 리밋은 코드 한 줄이 아니라 운영 정책입니다.

1. 제한 키가 무엇인지 정의합니다. IP, 사용자, API 키, 조직 중 무엇인가?
2. 읽기·쓰기·무거운 작업에 같은 한도를 적용할지 결정합니다.
3. 프록시 뒤에서 실제 클라이언트 IP를 신뢰할 수 있게 설정했는지 확인합니다.
4. 분산 서버 환경에서 카운터가 모든 인스턴스에 일관되게 적용되는지 확인합니다.
5. 실패율, 429 수, 상위 제한 대상, 대기열 길이를 관측합니다.
6. 관리자·내부 작업·웹훅에 별도 정책이 필요한지 검토합니다.
7. 제한값을 고객 API에 문서화할지 결정합니다.

Redis의 원자적 연산이나 API 게이트웨이를 이용하면 여러 서버 인스턴스가 같은 제한 상태를 공유하도록 설계할 수 있습니다. Redis 장애 시 모두 허용할지, 모두 제한할지도 서비스 위험도에 따라 결정해야 합니다.

## 마무리

레이트 리밋은 사용자를 벌주는 기능이 아니라, 한 사용자나 장애 난 클라이언트가 전체 서비스를 느리게 만들지 않도록 하는 안전장치입니다.

핵심은 세 가지입니다. 제한은 API·사용자·작업의 성격에 맞게 설계하고, 429와 Retry-After로 클라이언트가 복구할 정보를 제공하며, 쓰기 요청 재시도는 멱등성 보장 없이는 자동화하지 않는 것입니다.

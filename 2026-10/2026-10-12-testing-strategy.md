# 테스트 전략

테스트의 목적은 “버그가 없다”고 선언하는 것이 아닙니다. 코드를 바꿀 때 위험한 부분을 빠르게 발견하고, 사용자가 실제로 겪을 실패를 줄이며, 팀이 안전하게 개선하도록 돕는 것입니다.

## 테스트 피라미드

- 단위 테스트: 계산, 검증, 변환, 권한 규칙처럼 작은 단위
- 통합 테스트: API, 인증, 데이터베이스, 여러 모듈의 연결
- E2E 테스트: 실제 사용자 흐름

단위 테스트는 빠르고 많이 작성할 수 있습니다. 통합 테스트는 시스템 경계의 불일치를 찾습니다. E2E 테스트는 로그인·결제·가입·관리 기능처럼 핵심 흐름에 집중해야 합니다. 모든 테스트를 E2E로 만들면 느리고 불안정해집니다.

## 사용자 중심 테스트

프론트엔드에서는 내부 상태와 함수 호출보다 사용자가 보는 결과를 확인합니다.

- 입력 오류가 필드 근처에 보이는가?
- 저장 중 중복 클릭이 막히는가?
- 저장 성공 후 최신 값이 보이는가?
- 실패했을 때 다음 행동을 알 수 있는가?
- 권한 없는 기능이 노출되지 않는가?

성공 흐름만으로는 부족합니다. 네트워크 오류, 토큰 만료, 동시 수정, 중복 요청, 긴 텍스트, 특수문자, 모바일 화면도 의도적으로 검증해야 합니다.

## 통합 테스트와 테스트 데이터

많은 버그는 함수 내부보다 시스템 경계에서 생깁니다. 프론트엔드 필드 이름과 DTO 불일치, 시간대 오류, 권한 누락, DB 제약 조건 불일치, 트랜잭션 일부 실패가 대표적입니다.

테스트에는 운영 개인정보를 사용하지 않습니다. 테스트 전용 DB, 명확한 테스트 계정, 격리된 데이터, 대체 결제·이메일 서비스가 필요합니다. 외부 서비스는 인터페이스 뒤로 분리해 단위 테스트에서는 성공·실패·지연을 제어하고, 별도 통합 테스트에서 실제 계약을 확인합니다.

## 불안정한 테스트와 커버리지

가끔만 실패하는 flaky test는 결국 팀이 결과를 무시하게 만듭니다. 고정 시간 대기, 테스트 간 데이터 공유, 실행 순서 의존, 외부 네트워크 의존을 제거하고 실제 완료 상태를 기준으로 기다려야 합니다.

커버리지는 누락 영역을 찾는 지도이지 목표가 아닙니다. 높은 커버리지가 결제·권한·삭제 같은 고위험 흐름의 검증을 보장하지는 않습니다.

운영 버그를 수정할 때는 재현하는 테스트를 먼저 만들고, 수정 뒤 통과하게 하며, 그 테스트를 회귀 방지 장치로 남깁니다.
